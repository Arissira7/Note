## 用户创建定时器到定时任务执行的流程

1. 任务创建阶段 (Creation)

   
   - 首先是用户通过 HTTP POST 请求访问 /xtimer/create_timer 这个API接口来创建定时器。主要是将用户的定时任务元数据（如 AppID、任务名称、Cron 表达式、回调 URL 等）存储到 MySQL 的 xtimer 表中。此时任务状态默认为 Unabled (未激活) ，还不会被调度系统感知

   
2. 激活与迁移阶段 (Activation & Migration)
   - （手动触发）当用户调用 EnableTimer 接口激活任务时，会触发关键的数据迁移（Migrator）流程：
     1. 状态更新 ：首先将数据库中该 Timer 的状态更新为 Enabled
     2. 预计算执行时间 ：系统会根据 Cron 表达式，计算该任务在未来一段时间内（例如未来一个小时）的所有执行时间点
     3. 双重存储 ：对于未来一段时间内（例如未来一小时内）的所有执行时间点，生成一个 TimerTask 记录，不是未来一小时的不生成：
        - MySQL ：存入 timer_task 表，作为全量持久化数据。
        - Redis ：使用 Redis Pipeline 执行 ZADD 命令，存入 Redis 的 ZSet (Sorted Set) 中。Key 是分桶 ID，value是定时任务的唯一ID，Score 是执行时间戳。这是为了实现高性能的延时队列查询。
   - （周期后台运行）对于一些早就激活但是由于当时激活的时候还没有到执行时间点的任务（即例如上面那些不是未来一小时的）：
     - 系统会有一个后台任务，每隔 30 分钟（可配置）扫描一次所有处于 Enabled 状态的 Timer。
     - 具体工作为全量扫一遍 mysql 中的定时器定义数据库，解析出未来 60 分钟的定时任务点，在 mysql 执行记录表中添加记录，并在 Redis 中进行批量打点

   
3. 调度阶段 (Scheduling)

   
   调度器 ( Scheduler ) 负责将二维分片切片并分发给触发器
   1. 调度器启动后，会创建一个 time.Ticker（代码中默认是 1 秒），进入一个周期性轮询：获取当前时间 n，读取配置桶数 （默认 5），关注需要处理的分片
   2. 双重处理 ：不仅处理 当前分钟 （ now ），还会同时尝试处理 上一分钟
      - 为什么要处理上一分钟？ 为了防止系统重启或抖动导致上一分钟的某些分片没来得及处理完，这是一种 补偿机制 。
      - 生成 Key ：对于每一个桶 ID（0 到 4），结合时间格式化（例如 202310271201 ），生成唯一的分布式锁 Key： time_bucket_lock_202310271201_0 。
   3. 分布式锁抢占 ：对于每一个生成的 Key（代表某分钟的某一个桶），调度器尝试去 Redis 抢占这个锁，抢锁动作提交到协程池中执行。并将锁的过期时间设置为70s
      - 为什么是 70s？
        - 必须 > 60s ：因为一个分片的时间跨度是 1 分钟。如果锁 30s 就过期了，而处理任务花了 40s，那么第 31s 时另一个节点可能会抢到锁并重复执行，导致 双重触发
        - 必须 < 120s ：为了容错。万一持有锁的节点挂了（死锁），锁需要在下一个周期前自动释放，避免该分片永久被锁死。虽然理论上 < 120s 即可，但为了安全起见，通常设置在 60s 到 90s 之间
   4. 任务分发 ：抢到锁的节点，负责将该二维分片的所有任务交给触发器组件。这一步也是提交到协程池中执行

   
4. 触发阶段 (Triggering)

   触发器 ( Trigger ) 负责从 Redis 中精准捞取到期的任务：

   触发器内部会以 1 秒为周期对二维分片进行 ZRange 查询。
   1. 查询 ZSet ：它从 Redis ZSet 中拉取当前秒数（Score）范围内的任务 ID。
      - 兜底策略 ：如果 Redis 挂了或查不到，会降级去查 MySQL，保证任务不丢失。
   2. 提交执行 ：捞取到的任务会被提交到内存中的协程池中等待执行。
   - 一个分片内任务全部被触发后（还不一定确定这些任务能否被执行），延长这个分片的分布式锁时间到130s
     - 为什么是130s

       下一分钟会对上一分钟的任务重试，即完整调度一遍上一分钟的分片。目的是确保上一分钟的任务如果有执行失败的任务（因为失败释放了锁）可以在这一分钟里重新执行。设置130s是防止上一分钟成功执行的任务被重复执行

   
5. 执行阶段 (Execution)

   最后是执行器 ( Executor ) 真正运行任务：
   1. 获取最新定义 ：Worker 拿到任务 ID 后，会先去 DB 查一下 Timer 的最新定义（防止用户中途修改了回调地址或停用了任务）

      这一步，维护了mysql和redis的一致性
   2. HTTP 回调 ：根据 Timer 定义的 URL 和参数，发起 HTTP POST 请求通知业务方。
   3. 结果回写 ：执行完成后，将执行结果（成功/失败、响应内容）更新回 MySQL 的 timer_task 表，完成整个闭环。

## 用户创建定时器到定时任务执行的全链路物理流转流程

我们假设一个典型的生产环境物理拓扑：

- 客户端 ：用户的业务服务器。
- 负载均衡 (LB) ：Nginx 或 SLB。
- xtimer 集群 ：3 台物理机（Node A, Node B, Node C），每台都部署了相同的 xtimer-go 二进制文件。
- 存储层 ：
  - MySQL 集群 （主从架构）。
  - Redis 集群 （多节点 Cluster）。
    下面是 从创建到执行 的全链路物理流转图：

### 第一阶段：任务创建（写入路径）

场景 ：用户请求创建一个“每天 12:00 执行”的任务。

1. 请求路由 ：
   - 用户的请求打到 LB 。
   - LB 根据负载均衡算法，将请求随机转发给了 Node A 。
2. 落库（Node A -> MySQL） ：
   - Node A 解析 Cron 表达式。
   - Node A 发起 TCP 连接，将任务元数据（Cron, 回调地址等）写入 MySQL 主库 。
   - （此时 Node B 和 Node C 对此一无所知，它们只管干自己的活） 。
3. 急单处理（Node A -> Redis） ：
   - Node A 会判断：这个任务是不是 下一分钟 就要执行？
   - 如果是， Node A 会立刻计算出下一次执行时间，并发起 TCP 连接，直接把这个任务点写入 Redis 集群 的对应分桶 ZSet 中。
   - （这叫同步激活，保证刚创建的急单不漏跑） 。

### 第二阶段：异步迁移（预加载路径）

场景 ：任务是明天的，或者定时的。

1. 全员扫描 ：
   - Node A, B, C 上都有一个 Migrator 协程在后台跑（比如每 20 分钟醒一次）。
2. 数据搬运（Node X -> MySQL -> Redis） ：
   - 假设这次是 Node B 的 Migrator 抢到了迁移任务的锁（或者分片扫描）。
   - Node B 从 MySQL 从库 批量拉取未来 1 小时需要执行的任务。
   - Node B 在本地内存计算好执行时间点。
   - Node B 通过 Pipeline 批量将这些任务点（TaskID + RunTime）推送到 Redis 集群 的 ZSet 中。
   - （此时，Redis 变成了“待办事项清单”，里面存好了全球所有节点未来一小时要干的活） 。

### 第三阶段：分布式协同（抢锁路径）

场景 ：时间到了 12:00:00。

1. 全员苏醒 ：
   - Node A, B, C 的调度器（Scheduler）同时收到 Ticker 的信号醒来。
   - 它们各自在本地计算：现在是 12:00，涉及的分桶是 bucket_0 到 bucket_9 。
2. 网络竞速（App Nodes -> Redis） ：
   - Node A 向 Redis 发送： SETNX lock_12:00_bucket_0 。
   - Node B 向 Redis 发送： SETNX lock_12:00_bucket_0 。
   - Node C 向 Redis 发送： SETNX lock_12:00_bucket_1 。
3. 裁判裁决 ：
   - Redis 集群 收到请求。假设 Node A 的包先到，Redis 记录 Node A 赢了 bucket_0 。Node B 的请求后到，Redis 返回失败。
   - （结果：Node A 拿到了处理 bucket_0 的“令牌”，Node C 拿到了 bucket_1 的“令牌”） 。

### 第四阶段：任务触发（执行路径）

场景 ：Node A 抢到了 bucket_0 的锁，且该桶里有刚才创建的任务。

1. 拉取任务（Node A <-> Redis） ：
   - Node A 持有令牌，向 Redis 集群 发起 ZRANGE 查询： “把 bucket_0 里 12:00 分这一秒的任务给我。”
   - Redis 将任务 ID 列表（List of TaskIDs）通过网络返回给 Node A 。
2. 二次校验（Node A <-> MySQL） ：
   - Node A 拿到 ID 后，为了保险，可能会（取决于配置）去 MySQL 查一下： “这任务没被用户暂停吧？”
   - 确认状态为 Enabled 。
3. 内存派单（Node A 内部） ：
   - Node A 将任务丢进自己进程内的 协程池（Ants Pool） 。
4. 最终回调（Node A -> 用户服务） ：
   - 协程池里的一个 Worker 协程启动。
   - 它发起一个 HTTP POST 请求，打到 用户的业务服务器 。
   - 用户收到请求，业务逻辑执行完毕。

## 一秒钟同时执行 10,000 个任务，物理流程是怎样的？

假设配置了 bucketsNum: 100 ，部署了 10 台 xtimer 机器（Node 1-10）。

- 分流（Hashing & Sharding）
  - 这 10,000 个任务的 ID 会被哈希算法均匀分散到 100 个桶里。
  - 平均每个桶（Bucket）里有 100 个任务 。
- 并行抢锁（Locking）
  - 12:00:00 这一刻，10 台机器同时醒来，去抢这 100 个桶的锁。
  - 理想情况下，每台机器大概能抢到 10 个桶 。
- 批量拉取（Batch Fetching）
  - Node 1 抢到了 Bucket 5，它向 Redis 发起 ZRANGE 。
  - Redis 从内存跳表中直接截取 Bucket 5 的 100 个任务 ID，通过网络一次性返回给 Node 1。
  - （注意：Redis 只需要处理 100 次 ZRANGE 请求，而不是 10,000 次请求） 。
- 并发执行（Parallel Execution）
  - Node 1 拿到 1000 个任务（10 个桶 * 100 任务）。
  - Node 1 的 Ants 协程池 （容量假设 5000）瞬间从池子里借出 1000 个 Goroutine。
  - 这 1000 个 Goroutine 同时 向外部发起 HTTP 回调。
- 瓶颈在哪里？
  - Redis ：轻松扛住（100 QPS 的 ZRANGE 毫无压力）。
  - xtimer ：轻松扛住（Go 处理 1000 并发协程是小菜一碟）。
  - 真正的瓶颈 ： 用户的业务服务器 。如果你的一万个任务是回调同一个业务接口，那用户的服务器瞬间会收到 10,000 QPS 的 HTTP 流量冲击，大概率会挂掉。
