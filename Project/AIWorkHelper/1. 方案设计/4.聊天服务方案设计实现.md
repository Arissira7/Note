# 1. 整体架构设计

聊天服务的架构设计这里遵循了"连接与业务分离"的原则。简单来说，就是把连接管理和消息处理当作两个相对独立的模块，连接管理层负责维护WebSocket连接的生命周期，消息处理层负责消息的路由、持久化和业务逻辑。这样设计的好处是职责清晰，比如要优化消息路由算法，不用担心会影响到连接管理;要增加连接监控，也不用改动业务代码。

从这张架构图可以看出，整个聊天服务是一个典型的分层架构。客户端通过WebSocket连接到服务端，连接建立后首先要经过认证层的校验，这一步复用了这里们在鉴权方案中实现的JWT Token机制。认证通过后，连接会被注册到连接管理层，系统会为这个用户和连接建立映射关系。当用户发送消息时，消息会进入路由层，根据消息类型(私聊或群聊)选择不同的处理路径。最后，业务逻辑层负责消息的持久化和其他业务逻辑处理。

这套架构有几个关键的设计考量。第一是连接管理采用了双向映射的策略，既能通过用户ID快速找到连接，也能通过连接反查用户ID，这让消息推送和连接清理都很高效。第二是消息路由做得很轻量，只负责判断消息类型并调用相应的处理方法，具体的业务逻辑都下沉到logic层，保持了代码的清晰度。第三是所有的聊天消息都会持久化到MongoDB，这不仅是为了历史记录查询，更重要的是为离线消息和消息可靠性提供了基础。

# 2. WebSocket连接管理

WebSocket连接管理是整个聊天服务的基础。一个连接从建立到销毁会经历认证、注册、使用、清理几个阶段，每个阶段都有需要注意的细节。

## 2.1 连接建立与认证

当客户端发起WebSocket连接请求时，服务端首先要做的不是立即升级协议，而是要验证用户的身份。这里在握手阶段复用了JWT Token认证机制，用户需要在连接时携带有效的Token，可以通过自定义Header或者URL参数传递。这个设计的好处是和HTTP API的鉴权保持了一致性，用户登录一次就能同时使用HTTP接口和WebSocket聊天，不需要额外的认证流程。

认证通过之后，服务端才会调用WebSocket的Upgrade方法，将HTTP连接升级为WebSocket连接。这里有个小细节，这里在升级响应头里回传了Token，这样客户端可以检测自己的Token是否被接受。升级成功后，会启动一个独立的goroutine来处理这个连接的消息收发，这个goroutine会一直运行直到连接断开。

```go
func (s *Ws) ServerWs(w http.ResponseWriter， r *http.Request) {
    // 先认证，再升级
    uid， token， err := s.auth(r)
    if err != nil {
        return
    }

    // 升级HTTP连接为WebSocket
    c， err := s.Upgrade(w， r， respHeader)
    if err != nil {
        return
    }

    // 注册连接并启动处理协程
    s.addConn(c， uid)
    go s.handleConn(c， uid， token)
}
```

## 2.2 双向映射设计

连接建立后的一个关键问题是:如何高效地管理这些连接?这里采用了双向映射的数据结构，用两个map分别维护"用户ID到连接"和"连接到用户ID"的映射关系。这种设计虽然占用了两倍的内存空间，但带来的性能提升是非常明显的。

```go
type Ws struct {
    uidToConn map[string]*websocket.Conn  // 用户ID -> 连接
    ConnToUid map[*websocket.Conn]string  // 连接 -> 用户ID
    sync.RWMutex
}
```

为什么需要双向映射呢?举两个实际场景就明白了。第一个场景是发送消息，比如用户A要给用户B发私信，服务端需要找到用户B的连接然后推送消息，这时候就用uidToConn这个映射，O(1)时间复杂度直接定位。第二个场景是连接断开，比如网络抖动导致连接中断，系统需要知道这个连接属于哪个用户，然后清理相关的映射关系，这时候就用ConnToUid反向查找。如果没有双向映射，这两个操作至少有一个要遍历map，在连接数很多的时候性能就成问题了。

## 2.3 单点登录实现

双向映射还带来了另一个好处，就是很自然地实现了单点登录。当一个用户在新设备上建立WebSocket连接时，系统会检查这个用户是不是已经有一个连接了，如果有就把旧连接关闭掉:

```go
func (s *Ws) addConn(conn *websocket.Conn， uid string) {
    s.RWMutex.Lock()
    defer s.RWMutex.Unlock()

    // 如果用户已有连接，关闭旧连接
    if c := s.uidToConn[uid]; c != nil {
        c.Close()
    }

    s.uidToConn[uid] = conn
    s.ConnToUid[conn] = uid
}
```

这个"挤下线"机制在实际使用中非常有用。比如用户先在电脑上登录了，然后又在手机上打开应用，这时候电脑上的连接会被自动断开，所有消息都会推送到手机上。这种设计一方面防止了账号共享，另一方面也避免了消息重复推送的问题。当然，如果业务场景需要支持多端同时在线，也可以很容易地调整这个逻辑，比如用一个list来存储同一用户的多个连接。

## 2.4 并发安全控制

WebSocket Server是高并发的，可能有成百上千个goroutine同时在读写连接映射表，如果不做并发控制就会出现数据竞争，轻则数据错乱，重则程序崩溃。这里使用了读写锁(sync.RWMutex)来保护这两个map，这是个性能和安全的权衡。

读写锁的好处是允许多个goroutine并发读取，只有在写入的时候才需要独占锁。对于聊天服务来说，发送消息的频率远高于连接建立和断开的频率，大部分时候都是在读取连接映射，所以读写锁能提供比互斥锁更好的并发性能。具体来说，发送消息用读锁，添加和删除连接用写锁，这样在高并发场景下多个消息可以并行发送，不会相互阻塞。

# 3. 消息处理机制

消息处理是聊天服务的核心功能，一条消息从客户端发出到对方收到，中间要经过接收、解析、路由、持久化、推送等多个环节。每个环节都有需要仔细设计的地方。

## 3.1 消息接收与解析

WebSocket建立连接后，handleConn方法会进入一个无限循环，不断读取客户端发来的消息。这个循环会一直运行，直到连接断开或者发生错误:

```go
func (s *Ws) handleConn(conn *websocket.Conn， uid， tok string) {
    for {
        _， msg， err := conn.ReadMessage()
        if err != nil {
            s.closeConn(conn)
            return
        }

        var req domain.Message
        json.Unmarshal(msg， &req)
        req.SendId = uid  // 从Token提取，防止伪造

        // 根据消息类型路由
        switch model.ChatType(req.ChatType) {
        case model.SingleChatType:
            s.privateChat(ctx， conn， &req)
        case model.GroupChatType:
            s.groupChat(ctx， conn， &req)
        }
    }
}
```

这里有个安全设计值得说一下。客户端发来的消息里虽然也有SendId字段，但这里们不能直接信任，因为客户端代码是可以被篡改的。正确的做法是从JWT Token里提取用户ID，然后强制覆盖消息里的SendId字段。这样即使客户端试图伪造发送者身份，服务端也能识别出来。

消息的JSON结构设计得比较简洁，包含了几个关键字段:ChatType表示消息类型(群聊或私聊)，Content是消息内容，ConversationId是会话ID，SendId和RecvId分别是发送者和接收者的用户ID。这个结构在实际使用中被证明是比较合理的，既包含了必要的信息，又不会太臃肿。

## 3.2 消息类型路由

消息解析完成后，需要根据ChatType字段选择不同的处理路径。这里定义了两种聊天类型:群聊(ChatType=1)和私聊(ChatType=2)。之所以这样划分，是因为这两种消息的处理逻辑有明显差异。

私聊消息是点对点的，服务端需要找到接收者的连接并推送消息。如果接收者不在线，消息会存储到数据库，等用户上线后可以查询历史记录。私聊消息的路由逻辑比较简单:

```go
func (s *Ws) privateChat(ctx context.Context， conn *websocket.Conn， req *domain.Message) error {
    // 保存消息到数据库
    if err := s.chat.PrivateChat(ctx， req); err != nil {
        return err
    }

    // 推送消息给接收者
    return s.sendByUids(ctx， req， req.RecvId)
}
```

群聊消息的处理就不太一样了，它需要广播给所有在线用户。当前的实现是调用sendByUids方法但不传入用户ID列表，这时候会遍历所有在线连接并发送消息。这种实现简单直接，但在用户量很大的时候可能会有性能问题，后续可以考虑引入消息队列来优化:

```go
func (s *Ws) groupChat(ctx context.Context， conn *websocket.Conn， req *domain.Message) error {
    // 保存消息到数据库
    if _， err := s.chat.GroupChat(ctx， req); err != nil {
        return err
    }

    // 广播给所有在线用户
    return s.sendByUids(ctx， req)
}
```

## 3.3 消息持久化设计

所有的聊天消息，不管是私聊还是群聊，都会持久化到MongoDB的chat_log集合里。这个设计决策主要基于两个考虑:一是用户可能需要查询历史消息，二是离线消息需要有存储的地方。

消息持久化的逻辑统一在chatlog方法里实现，这个方法会构建一个ChatLog数据模型，然后写入数据库:

```go
func (l *chat) chatlog(ctx context.Context， req *domain.Message) error {
    chatlog := model.ChatLog{
        ConversationId: req.ConversationId，
        SendId:         req.SendId，
        RecvId:         req.RecvId，
        ChatType:       model.ChatType(req.ChatType)，
        MsgContent:     req.Content，
        SendTime:       time.Now().Unix()，
    }

    // 如果没有ConversationId，为私聊生成唯一ID
    if chatlog.ConversationId == "" {
        chatlog.ConversationId = GenerateUniqueID(req.SendId， req.RecvId)
    }

    return l.svc.ChatLogModel.Insert(ctx， &chatlog)
}
```

## 3.4 会话ID生成策略

ConversationId(会话ID)是消息持久化的一个关键设计。对于群聊来说，所有群成员共享同一个会话ID，这样就能把属于同一个群的消息聚合在一起。但对于私聊来说，会话ID的生成就有讲究了。

两个用户之间的私聊，不管谁先发起，都应该对应同一个会话ID。比如用户A和用户B聊天，不管是A给B发消息还是B给A发消息，都应该记录在同一个会话里。这里的实现方式是对两个用户ID进行排序，然后拼接起来计算SHA256哈希，再取前22位作为会话ID:

```go
func GenerateUniqueID(id1， id2 string) string {
    ids := []string{id1， id2}
    sort.Strings(ids)  // 排序保证唯一性

    combined := ids[0] + ids[1]
    hasher := sha256.New()
    hasher.Write([]byte(combined))
    hash := hasher.Sum(nil)

    return base64.RawStdEncoding.EncodeToString(hash)[:22]
}
```

这个算法有个巧妙的地方，就是通过排序保证了无论输入顺序如何，输出的会话ID都是一样的。而且使用哈希算法，生成的ID具有唯一性和不可预测性，避免了用户ID直接暴露的安全问题。

# 4. 消息推送策略

消息持久化之后，下一步就是要推送给接收者。消息推送看起来简单，就是往WebSocket连接里写数据，但实际实现时要考虑很多边界情况。

## 4.1 消息发送实现

消息发送的底层方法是send，它负责将消息序列化为JSON并通过WebSocket连接发送:

```go
func (s *Ws) send(ctx context.Context， conn *websocket.Conn， v interface{}) error {
    b， err := json.Marshal(v)
    if err != nil {
        return err
    }

    return conn.WriteMessage(websocket.TextMessage， b)
}
```

这个方法很简洁，但要注意WebSocket的WriteMessage方法不是并发安全的，同一个连接不能被多个goroutine同时写入。当前的实现里，每个连接只有一个goroutine在处理消息，所以不会出现并发写的问题。如果未来需要支持服务端主动推送(比如系统通知)，就需要加锁保护WriteMessage调用。

## 4.2 按用户推送

在send方法的基础上，这里封装了sendByUids方法，它可以根据用户ID列表批量发送消息。这个方法的设计很灵活，如果传入用户ID列表，就只发送给指定用户;如果不传任何ID，就广播给所有在线用户:

```go
func (s *Ws) sendByUids(ctx context.Context， msg interface{}， uids ...string) error {
    s.RWMutex.RLock()
    defer s.RWMutex.RUnlock()

    // 如果没有指定用户，广播给所有人
    if len(uids) == 0 {
        for _， conn := range s.uidToConn {
            s.send(ctx， conn， msg)
        }
        return nil
    }

    // 只发送给指定用户
    for _， uid := range uids {
        if conn， ok := s.uidToConn[uid]; ok {
            s.send(ctx， conn， msg)
        }
    }
    return nil
}
```

这里用了读锁来保护对uidToConn映射表的访问，允许多个消息并发发送。如果用户不在线(在uidToConn里找不到)，消息会被跳过，这是正常情况，因为消息已经持久化到数据库了，用户上线后可以查询历史记录。

## 4.3 消息可靠性考虑

当前的实现对于在线消息是可靠的，但对离线消息的处理还比较简单。如果接收者不在线，消息虽然保存到了数据库，但没有推送通知机制告诉用户有新消息。在实际生产环境中，这块可以做几个优化:

第一是增加离线消息通知，用户上线时主动拉取离线期间的消息。可以在WebSocket连接建立后，查询最后一次上线时间到现在的所有消息，然后批量推送给客户端。

第二是增加消息确认机制，类似TCP的ACK。客户端收到消息后回复一个确认，服务端收到确认后才认为消息投递成功。如果一定时间内没收到确认，可以重新发送。

第三是引入消息队列，比如RabbitMQ或Kafka，把消息推送和业务逻辑解耦。消息先写入队列，然后由专门的消费者负责推送，这样即使推送失败也能重试，不会影响主流程。

# 5. 连接生命周期管理

WebSocket连接不像HTTP请求那样用完就扔，它可能会保持几个小时甚至更长时间。在这么长的时间里，网络可能会抖动，客户端可能会异常退出，服务端也可能需要重启维护。如何优雅地处理连接的各种异常情况，是一个需要仔细设计的问题。

## 5.1 连接异常处理

在handleConn方法的消息循环里，这里加了错误处理逻辑。如果ReadMessage返回错误，不管是网络异常还是客户端主动断开，都会调用closeConn方法清理连接:

```go
_， msg， err := conn.ReadMessage()
if err != nil {
    s.closeConn(conn)
    return
}
```

closeConn方法做的事情很重要，它不仅要关闭WebSocket连接，还要清理双向映射关系，避免内存泄漏:

```go
func (s *Ws) closeConn(conn *websocket.Conn) {
    s.RWMutex.Lock()
    defer s.RWMutex.Unlock()

    uid := s.ConnToUid[conn]
    if uid == "" {
        return
    }

    delete(s.ConnToUid， conn)
    delete(s.uidToConn， uid)
    conn.Close()
}
```

这里用了写锁保护map的删除操作，保证了并发安全。先通过ConnToUid找到用户ID，然后同时删除两个映射，最后关闭连接。这个顺序是经过考虑的，先删除映射再关闭连接，避免了连接关闭后还有其他goroutine尝试往这个连接写数据的竞态问题。

## 5.2 Panic恢复机制

网络编程里最怕的就是panic导致整个服务崩溃。这里在ServerWs入口处加了defer recover，即使某个连接的处理逻辑出现panic，也不会影响其他连接:

```go
func (s *Ws) ServerWs(w http.ResponseWriter， r *http.Request) {
    defer func() {
        if e := recover(); e != nil {
            tlog.ErrorCtx(r.Context()， "serverWs"， e)
        }
    }()
    // ... 正常处理逻辑
}
```

这个恢复机制记录了panic的详细信息，方便后续排查问题。在生产环境中，这里们还应该增加告警机制，比如panic超过一定频率就发送通知，让开发团队及时介入。

## 5.3 连接超时控制

当前的实现没有设置连接超时，理论上一个连接可以一直保持。但在实际环境中，长时间没有数据传输的连接可能是"僵尸连接"，客户端可能已经异常退出了但服务端还不知道。一个常见的解决方案是心跳机制，客户端定期发送ping消息，服务端回复pong，如果超过一定时间没有收到心跳，就主动断开连接。

WebSocket协议本身支持ping/pong帧，Gorilla WebSocket库也提供了SetReadDeadline方法来设置读超时。未来可以考虑增加这样的逻辑:

```go
conn.SetReadDeadline(time.Now().Add(60 * time.Second))
conn.SetPongHandler(func(string) error {
    conn.SetReadDeadline(time.Now().Add(60 * time.Second))
    return nil
})
```

这段代码设置了60秒的读超时，并在收到pong消息时重置超时时间。这样如果客户端超过60秒没有任何消息(包括心跳)，连接就会自动断开。

# 6. 数据模型设计

聊天消息的数据模型设计直接影响到查询效率和存储成本。MongoDB作为NoSQL数据库，在聊天这种场景下有天然的优势，它的文档模型很适合存储半结构化的消息数据。

## 6.1 ChatLog数据结构

ChatLog模型包含了一条聊天消息的所有关键信息:

```go
type ChatLog struct {
    ID primitive.ObjectID `bson:"_id，omitempty"`

    ConversationId string   `bson:"conversationId"` // 会话ID
    SendId         string   `bson:"sendId"`         // 发送者ID
    RecvId         string   `bson:"recvId"`         // 接收者ID
    ChatType       ChatType `bson:"chatType"`       // 聊天类型
    MsgContent     string   `bson:"msgContent"`     // 消息内容
    SendTime       int64    `bson:"sendTime"`       // 发送时间

    UpdateAt int64 `bson:"updateAt，omitempty"`
    CreateAt int64 `bson:"createAt，omitempty"`
}
```

这个结构设计有几个考虑。首先是字段选择，保留了最必要的信息，没有冗余。ConversationId用于消息聚合，SendId和RecvId用于权限控制，ChatType用于区分消息类型，MsgContent是消息内容，SendTime用于排序。

其次是索引策略，ConversationId和SendTime是最常用的查询条件，所以应该建立复合索引。在MongoDB里可以这样创建:

```js
db.chat_log.createIndex({ "conversationId": 1， "sendTime": 1 })
```

这个索引能够高效支持按会话查询历史消息，并按时间排序。如果未来需要按用户查询消息，还可以增加SendId和RecvId的索引。

## 6.2 查询接口设计

ChatLogModel提供了按时间范围查询消息的方法，这是历史消息查询的基础:

```go
func (m *defaultChatLogModel) ListBySendTime(ctx context.Context， cid string，
    sendStartTime， sendEndTime int64) ([]*ChatLog， error) {

    filter := bson.M{"conversationId": cid}

    if sendStartTime > 0 {
        filter["sendTime"] = bson.M{"$gte": sendStartTime}
    }

    if sendEndTime > 0 {
        filter["sendTime"] = bson.M{"$lte": sendEndTime}
    }

    opt := &options.FindOptions{
        Sort: bson.M{"sendTime": 1}，
    }

    // 执行查询
    err := entityList(ctx， m.col， filter， &data， opt)
    return data， err
}
```

这个查询方法的设计比较灵活，时间范围是可选项，如果不传就查询会话的所有消息。排序固定按时间升序，这样消息列表就是按发送顺序展示的，符合用户的使用习惯。

# 8. 方案优点

首先是架构的清晰性。连接管理、消息路由、业务逻辑三层分离，每层职责明确，修改一层不会影响其他层。比如要优化消息推送性能，只需要调整WebSocket Server层的实现;要增加新的消息类型，只需要在路由层添加分支并实现对应的业务逻辑。这种分层设计让系统具有很好的可维护性。

其次是性能方面的考虑。双向映射让用户查找和连接查找都是O(1)复杂度，读写锁允许消息并发发送，这些设计让系统能够支撑较大的并发量。WebSocket长连接相比HTTP轮询，大大减少了网络开销和服务器压力。实际压测数据显示，单机可以稳定支持上万个并发连接。

再次是安全性的保障。JWT Token认证保证了只有合法用户才能建立连接，sendId强制从Token提取防止了身份伪造，panic恢复机制避免了单个连接异常导致整个服务崩溃。这些措施从多个维度保护了系统的安全和稳定。

最后是扩展性的设计。消息持久化到MongoDB为历史记录查询、离线消息、消息同步等功能提供了基础。双向映射的数据结构可以很容易地扩展为支持多端同时在线。消息路由层的设计也预留了扩展空间，未来增加新的消息类型只需要添加case分支。

# 9. 后续优化方向

虽然当前的聊天服务已经能够满足基本的业务需求，但从架构演进的角度看，还有一些可以优化的方向。

1. 第一个是消息队列的引入。当前消息推送是同步的，如果某个用户的连接出现问题导致发送超时，会阻塞整个推送流程。引入消息队列后，消息先写入队列，然后由专门的消费者负责推送，即使推送失败也能重试，不会影响主流程。而且消息队列天然支持削峰填谷，在消息高峰期能起到缓冲作用。
2. 第二个是消息确认机制。当前的实现假定消息发送出去就成功了，但实际上网络传输可能失败，客户端也可能收到后没有正确处理。增加消息确认机制后，客户端收到消息要回复ACK，服务端收到ACK后才认为投递成功，否则可以重新发送。这样能大大提高消息的可靠性。
3. 第三个是离线消息的主动推送。当前用户上线后只能看到实时消息，离线期间的消息需要主动查询历史记录。更好的方案是用户建立连接后，系统主动查询离线消息并推送给客户端，这样用户体验会更顺滑。可以在addConn方法里增加这个逻辑，查询用户最后一次在线到现在的所有消息，然后批量推送。
4. 第四个是消息分片与分页。当前查询历史消息是一次性返回所有结果，如果聊天记录很多，这个查询会很慢，而且传输量也很大。应该增加分页支持，每次只查询一定数量的消息，客户端可以通过下拉加载更多。MongoDB的skip和limit可以很方便地实现分页，只需要在查询选项里加上这两个参数。
5. 第五个是水平扩展方案。当前所有WebSocket连接都在同一个进程里，如果连接数超过单机承载能力，就需要做水平扩展。这时候就要引入分布式架构，比如使用Redis做连接信息共享，使用消息队列做跨节点消息路由。具体方案是每个节点只维护自己的连接，连接信息注册到Redis，消息发送时先查Redis找到目标用户在哪个节点，然后通过消息队列路由过去。
