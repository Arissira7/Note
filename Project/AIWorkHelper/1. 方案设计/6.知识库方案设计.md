# 1. 方案背景

在企业工作场景中,有大量的制度文档、操作手册、政策规范散落在各个角落,员工经常需要翻找各种PDF文档来查询信息。比如新员工想了解公司的请假制度,可能要在共享文件夹里找半天才能找到那个员工手册;老员工想确认一下报销流程的某个细节,也得打开几十页的PDF慢慢翻阅。这种传统的文档查询方式效率很低,而且找到文档后还要自己理解和提取关键信息。

这里就需要用到企业知识库来完成了。只需要先把这些知识库发送给AI，AI能够理解和检索这些知识，就可以直接让AI直接根据这些知识库的内容回答这些文档里的问题?用户只需要用自然语言问就可以了。

但要实现这个目标,技术上有不少挑战。首先是PDF的文本提取问题,特别是中文PDF,很多开源库处理不好会出现乱码或者文本错位;其次是如何把文档切分成合适的片段,既要保证每个片段有完整的语义,又不能太大导致检索不准确;再次是如何高效地检索,当知识库里有几十上百篇文档时,怎么快速找到和用户问题最相关的那几段内容;最后是如何让AI基于检索到的内容给出准确的答案,而不是胡编乱造。

在技术选型上,选择向量数据库来存储和检索文档内容。主要是由于传统的关键词检索在处理自然语言时效果很差,用户问"请假规定"和文档里写的"休假管理办法"明明是同一个意思,但关键词匹配就会miss掉。而向量检索是基于语义的,它会把文本转换为高维向量,语义相近的文本在向量空间中距离也相近,这样就能准确找到相关内容,即使用词不完全一样。

# 2. 整体架构设计

知识库系统的架构设计遵循了“文档处理-向量存储-语义检索-智能问答”的流程。整个系统可以分为文档处理层、向量化层、存储检索层、问答生成层四个核心部分,每一层都有明确的职责边界。

从这张架构图可以清晰地看出,知识库系统分为两条主要流程:文档更新流程和知识查询流程。

文档更新流程是这样的:用户上传PDF文档后,智能路由器会把请求分发给Knowledge处理器,处理器调用KnowledgeUpdate工具。这个工具首先使用PDFProcessor提取PDF中的文本内容,然后对文本进行清理和分块处理,每个块大小控制在500个字符左右。接着调用Embedder把每个文本块转换为向量,最后把向量和对应的文本内容、元数据一起存储到Redis向量数据库中。

知识查询流程相对更简单一些:用户提出问题后,路由器同样分发给Knowledge处理器,处理器调用KnowledgeRetrievalQA工具。这个工具使用RetrievalQA链来处理查询,首先把用户的问题也转换为向量,然后在向量数据库中进行相似度检索,找出最相关的文档片段,最后把检索到的内容和用户的问题一起发给LLM,让LLM基于这些内容生成答案。

这套架构有几个关键的设计考量：

1. 第一是文档处理和查询检索完全解耦,PDF处理的逻辑封装在PDFProcessor里,检索问答的逻辑封装在RetrievalQA链里,两者互不影响。
2. 第二是使用了LangChain的RetrievalQA链,这个链已经封装好了"检索-生成"的完整流程,我们不需要手动处理检索结果和提示词拼接。
3. 第三是向量化和存储都委托给成熟的组件,Embedder使用LLM提供的embedding能力,存储使用Redis Vector Store,都是经过验证的可靠方案。

# 3. PDF文档处理设计

PDF文档处理是知识库系统的第一步,也是最容易出问题的一步。早期这块功能尝试过几个PDF处理库,包括pdfcpu、unidoc等,但在处理中文PDF时都遇到了各种问题:有的提取出来的文本顺序混乱,有的中文字符显示为乱码,有的根本提取不出文本。经过多次尝试,最终选择了go-fitz这个库,它基于MuPDF引擎,对中文的支持非常好。

## 3.1 PDF文本提取流程

文本提取的核心流程是逐页读取PDF内容,然后对提取出来的文本进行清理和标准化处理。这个过程看似简单,但实际上有很多细节需要处理。

从这个时序图可以看到,PDF文本提取的过程是非常严谨的。首先会验证文件是否存在,避免后续处理出现文件不存在的错误。然后使用go-fitz打开PDF文档,获取文档的总页数。接下来逐页提取文本内容,这里有个重要的容错设计:如果某一页提取失败,系统会记录警告但继续处理其他页面,而不是直接中断整个流程。这样设计的原因是,有些PDF可能某几页有特殊的编码或者是扫描件,但其他页面的内容是可以正常提取的,我们不能因为个别页面失败就放弃整个文档。

提取完所有页面后,系统会调用cleanText方法对文本进行清理。这个清理过程主要做几件事:去除多余的空白字符、把多个连续的空行合并为单个空行、标准化换行符。这些看似简单的操作,对后续的分块和检索质量影响很大。如果不做清理,可能会出现一个文档块里全是空行,或者因为空白字符太多导致分块不准确的情况。

## 3.2 文档分块策略

文档提取出来后,需要切分成适当大小的块。这个块的大小非常关键:太小了语义不完整,检索效果差;太大了包含的信息太多,检索时容易把不相关的内容也带进来,而且LLM的上下文窗口也有限制。经过实际测试,这里把每个块的大小设置为500个字符,块与块之间有50个字符的重叠。

重叠设计是为了避免语义被切断的问题。假设一段完整的句子"请假超过3天需要部门主管和人事部门共同审批",如果正好被切在"部门主管"和"人事部门"之间,那么两个块各自都只有部分信息,检索时可能匹配不准确。通过设置50个字符的重叠,可以大大降低这种情况的发生概率。

```go
func (p *PDFProcessor) splitText(text string, chunkSize int, chunkOverlap int) []string {
    if chunkSize <= 0 {
        chunkSize = 1000 // 默认块大小
    }
    if chunkOverlap < 0 {
        chunkOverlap = 0
    }

    var chunks []string
    textRunes := []rune(text) // 使用rune来正确处理中文字符
    textLen := len(textRunes)

    start := 0
    for start < textLen {
        end := start + chunkSize
        if end > textLen {
            end = textLen
        }

        chunk := string(textRunes[start:end])
        chunk = strings.TrimSpace(chunk)

        if len(chunk) > 0 {
            chunks = append(chunks, chunk)
        }

        // 计算下一个块的起始位置
        if end >= textLen {
            break
        }
        start = end - chunkOverlap
        if start < 0 {
            start = 0
        }
    }

    return chunks
}
```

这段代码有个重要的细节:使用`[]rune`而不是直接操作字符串。在Go语言中,字符串是以字节为单位的,一个中文字符通常占3个字节,如果直接按字节切分,很可能把一个中文字符切成两半,导致乱码。转换为`[]rune`后,每个元素代表一个完整的Unicode字符,无论是英文字母还是中文汉字都按一个字符计算,这样切分就不会破坏字符的完整性。

## 3.3 文档元数据管理

每个文档块在存储时都会附带元数据,这些元数据对于后续的检索和溯源非常重要。这里为每个块记录了文档来源路径和页码信息:

```go
documents[i] = schema.Document{
    PageContent: chunk,
    Metadata: map[string]any{
        "source": filePath,
        "page":   i + 1,
    },
}
```

这样设计的好处是,当AI回答用户问题时,不仅能给出答案,还能告诉用户这个信息来自哪个文档的第几页,用户如果需要查看原文就可以直接定位。这种可溯源性在企业场景中特别重要,有些政策性的信息用户可能需要看原文才放心。

# 4. 向量化与存储设计

文档处理完成后,接下来就是向量化和存储的环节。向量化是语义检索的基础,它把文本从人类可读的自然语言转换为计算机可以计算相似度的数学向量。

## 4.1 向量化原理

向量化(Embedding) 是一种将词语、句子或文档转换成数字向量的技术。它通过将高维、离散的输入数据（如文本、图像、声音等）映射到低维、连续的向量空间中，使得计算机能够更好地理解和处理这些数据。

在知识库（RAG）技术中，可以简单理解为，embedding 模型是对知识库文件进行解析的。文本是由自然语言组成的，这种格式不利于机器直接计算相似度。embedding 模型要做的，就是将自然语言转化为高维向量，这样就可以很方便的通过向量来计算他们之间的相似度了，然后通过向量来捕捉到单词或句子背后的语义信息。

举个例子：

假设有“初中生”，“高中生”以及“大模型”三个词，embedding会将初中生和高中生映射到相近的向量空间中；而“大模型”会被映射到离他们较远的向量空间中

这样通过embeding，机器就可以学习到自然语言之间的深度语义关系，并且依此计算出不同文本之间的相似关系了

embedding不仅会对知识库的文本数据进行向量化解析，用户的输入同样会经过嵌入（Embedding）处理，生成一个高维向量。

拿用户的提问去匹配本地知识库的本质其实就是使用这个用户输入生成的这个高纬向量，去查询知识库中查找相似度高的向量。系统会利用某些相似度度量（如余弦相似度）去判断这个相似度。这一整个过程可以理解为，上传并解析了知识库之后，相当于给知识库中每一个小的文段都生成了一个指纹，然后用户输入问题之后，这个问题同样也会生成一个独一无二的指纹，接着知识库系统就会拿着用户输入的这个指纹，在指纹库也就是知识库中匹配，找到相似的指纹，然后把将检索到的这些相关文段与用户的输入结合，扩展模型的上下文，再喂给大模型。

LangChain提供的Embedder会调用底层的LLM生成向量。这里使用的是阿里云DashScope的embedding能力,这个模型在中文场景下表现很好。调用过程很简单:

```go
embedder, err := embeddings.NewEmbedder(svc.LLMs)
if err != nil {
    return nil, err
}
```

创建好Embedder之后,它会在需要时自动把文本转换为向量,我们不需要手动调用。这种封装让上层代码保持简洁,所有向量化的细节都被Embedder处理了。

## 4.2 Redis向量存储

向量生成后需要存储起来,这里选择了Redis作为向量数据库。这个选择主要基于几个考虑:

1. 首先Redis性能很好,能够支撑高并发的检索请求
2. 其次Redis向量搜索插件(RediSearch)提供了成熟的向量检索能力,支持余弦相似度、欧氏距离等多种相似度计算方法
3. 最重要的是,Redis本身就是我们技术栈的一部分,不需要额外引入新的组件

```go
func getKnowledgeStore(ctx context.Context, svc *svc.ServiceContext) (*redisvector.Store, error) {
    embedder, err := embeddings.NewEmbedder(svc.LLMs)
    if err != nil {
        return nil, err
    }

    return redisvector.New(ctx,
        redisvector.WithEmbedder(embedder),
        redisvector.WithConnectionURL("redis://"+svc.Config.Redis.Addr),
        redisvector.WithIndexName("knowledge", true))
}
```

这段代码创建了一个Redis向量存储实例,索引名称是"knowledge",这个索引专门用来存储知识库的向量数据。第三个参数`true`表示如果索引不存在就自动创建,这样可以简化初始化流程。

向量存储的过程是这样的:调用`store.AddDocuments(ctx, chunkedDocuments)`方法,把所有的文档块传入,Redis Vector Store会自动完成几件事:调用Embedder把每个文档块转换为向量、将向量和原始文本、元数据一起存储到Redis、更新向量索引以支持高效检索。整个过程我们只需要一行代码,底层的复杂性都被封装好了。

## 4.3 存储结构设计

Redis中的数据组织方式大致是这样的:

- 向量数据:每个文档块对应一个高维向量(维度由LLM的embedding模型决定,通常是512或1024维)
- 文本内容:原始的文档块文本,检索时需要返回给用户
- 元数据:文档来源、页码等信息,用于溯源

这三部分数据通过Redis的数据结构关联在一起。当我们进行向量检索时,Redis会:

1. 计算查询向量和库中所有向量的相似度
2. 按相似度排序,返回TopK个最相似的向量
3. 根据向量ID取出对应的文本内容和元数据
4. 组装成完整的文档对象返回

整个过程的时间复杂度经过优化后可以做到毫秒级,即使知识库里有成千上万个文档块,检索速度也能保持很快。

# 5. 语义检索与智能问答

文档存储好之后,最核心的功能就是根据用户的问题检索相关内容并生成答案。这个过程涉及到向量检索和LLM问答两个关键环节。

## 5.1 检索问答流程

当用户提出一个问题,比如"请假超过3天需要谁审批",系统的处理流程是这样的:

从这个详细的时序图可以清楚地看到,整个检索问答流程分为两个阶段:

向量检索阶段:首先把用户的问题也转换为向量,这个向量化过程和文档向量化使用的是同一个Embedder,保证了向量空间的一致性。然后在Redis向量库中进行相似度检索,计算问题向量和所有文档向量的余弦相似度,找出最相关的TopK个文档块。我这里设置TopK=1,也就是只取最相关的那一个文档块,这样可以避免引入过多不相关的内容干扰LLM的判断。

答案生成阶段:检索到相关文档后,RetrievalQA链会构建一个特殊的提示词,这个提示词包含两部分信息:检索到的文档内容作为Context,用户的问题作为Question。然后发送给LLM,让LLM基于Context来回答Question。这种设计有个关键优势:LLM不是凭空编造答案,而是基于真实的文档内容来回答,大大提高了答案的准确性和可信度。

## 5.2 检索参数优化

TopK的设置是一个需要权衡的参数。设置得太小,可能会遗漏一些相关信息;设置得太大,会引入太多噪音,而且LLM的上下文窗口也有限制。经过实际测试,我发现对于企业内部的知识库,TopK=1的效果最好。原因是企业文档通常结构清晰,一个具体的问题往往在某个特定的段落就能找到完整的答案,不需要多个段落拼凑。

如果未来知识库规模变大,或者问题变得更复杂,可以考虑把TopK调整为2或3。但要注意,增加TopK不是简单地提高准确率,它可能带来副作用:多个文档块可能包含矛盾的信息,或者某些块的内容不够相关,这都会影响LLM生成答案的质量。所以TopK的设置需要根据实际场景进行调优。

## 5.3 答案输出优化

KnowledgeRetrievalQA工具在返回答案时,会附加一个特殊的指令:

```go
return `The following are the consultation results. When outputting, please output the results directly, do not make summaries, keep them in Chinese, and only do the original output:
\n` + res, nil
```

这个指令的作用是引导LLM的输出格式。如果不加这个指令,LLM可能会对答案进行总结或者改写,有时候还会加上一些额外的解释,这些都不是我们想要的。通过明确告诉LLM"直接输出结果,不要做总结,保持中文",可以让答案更加简洁准确。

特别是"保持中文"这个要求很重要。因为我们使用的LLM模型是通用的,它可能会倾向于用英文或者中英文混合的方式回答,但我们的知识库是中文的,用户问的也是中文问题,答案自然应该是纯中文。这个显式的提示能够很好地解决这个问题。

# 6. 知识库更新机制

知识库不是一次性加载就完事的,企业的制度文档会不断更新,知识库也需要跟着更新。这里设计了一个简单而有效的更新机制。

## 6.1 文档更新流程

从这个流程图可以看到,知识库更新的过程做了很多容错处理。首先是对输入的解析做了两次尝试:先用结构化解析器解析,如果失败再尝试用JSON解析,这样可以兼容Agent输出格式不稳定的情况。然后是对文件路径做了规范化处理,支持相对路径和绝对路径两种方式,并且在处理前验证文件是否存在。PDF处理的过程也做了充分的错误检查,如果某个环节失败会返回明确的错误信息。

这种多层验证的设计让系统更加健壮。用户上传文档时可能会遇到各种问题:文件路径写错、PDF格式有问题、网络传输中断等等,如果每个错误都直接抛异常,用户体验会很差。通过友好的错误提示,用户能够明确知道哪里出了问题,该怎么修正。

## 6.2 增量更新策略

当前的实现是每次上传文档都会全量添加到向量库中。Redis Vector Store内部会处理去重和索引更新,如果同一个文档被重复上传,会覆盖之前的版本。这种设计简单直接,适合中小规模的知识库。

如果未来知识库规模扩大,需要更精细的更新策略,可以考虑这样优化:

- 为每个文档维护一个版本号或者更新时间戳
- 上传文档时先检查是否已存在该文档的旧版本
- 如果存在旧版本,先删除旧版本的所有文档块,再添加新版本
- 这样可以避免向量库中同时存在同一文档的多个版本,导致检索时返回过期内容

但目前的简单策略已经能够满足大部分需求,而且实现成本低,维护简单,这是我在权衡后的选择。

# 7. 知识库处理器设计

Knowledge处理器是知识库功能的统一入口,它配备了两个核心工具:KnowledgeUpdate和KnowledgeRetrievalQA,分别处理文档更新和知识查询两个场景。

## 7.1 处理器结构

```go
type Knowledge struct {
    *baseChat
}

func NewKnowledge(svc *svc.ServiceContext) *Knowledge {
    return &Knowledge{NewBaseChat(svc, []tools.Tool{
        toolx.NewKnowledgeUpdate(svc),
        toolx.NewKnowledgeRetrievalQA(svc),
    })}
}

func (t *Knowledge) Name() string {
    return "knowledge"
}

func (t *Knowledge) Description() string {
    return `This is the company's knowledge base.
Can answer employee consultation questions about company systems such as approval process, leave matters, attendance matters, employee manuals and other office content.
Can also be used for updating the knowledge base.`
}
```

这个处理器的设计很简洁,它继承了baseChat,所以自动具备了Agent执行能力。Description明确告诉路由器它的职责:回答员工关于公司制度的咨询,以及更新知识库。当路由器分析到用户的问题是"请假需要谁审批"或者"帮我上传员工手册"这类内容时,就会把请求分发给Knowledge处理器。

## 7.2 工具协作机制

Knowledge处理器配备的两个工具各司其职,通过Agent的自主决策来选择使用哪个工具。比如用户说"帮我上传这个PDF到知识库",Agent会分析出这是更新操作,调用KnowledgeUpdate工具;用户说"公司的考勤制度是什么",Agent会识别出这是查询操作,调用KnowledgeRetrievalQA工具。

这种设计的好处是扩展性强。如果未来要增加新的知识库功能,比如"删除某个文档"或者"列出所有文档",只需要实现新的工具并注册到Knowledge处理器的工具列表中,Agent会自动学会使用这些工具,不需要改动路由逻辑或者处理器的核心代码。

## 7.3 与其他处理器的配合

Knowledge处理器和其他处理器(Todo、Approval等)是平级的关系,它们都注册在智能路由器上。当用户的问题涉及多个领域时,路由器会选择最匹配的那个处理器。比如用户问"创建一个待办,内容是学习公司的考勤制度",路由器可能会优先选择Todo处理器,因为创建待办是主要意图;而如果用户问"公司的考勤制度是什么,我需要据此创建待办",路由器可能会选择Knowledge处理器,因为查询知识是第一步。

这种智能分发的能力依赖于路由器的LLM分析,不需要我们编写复杂的规则。每个处理器只需要把自己的Description写清楚,LLM就能根据用户的意图做出正确的判断。

# 9. 性能优化策略（面试点）

知识库系统在实际运行中也遇到了一些性能问题,经过优化后得到了明显改善。

1. 第一个优化是PDF处理的异步化。早期实现中,用户上传PDF后需要等待所有处理流程完成才能得到响应,对于大文件可能要等好几秒。后来我把PDF处理改为异步执行,用户上传后立即返回"正在处理",处理完成后通过WebSocket通知用户,这样用户体验好很多。
2. 第二个优化是向量检索的缓存。发现有些常见问题会被反复查询,比如"请假制度"、"报销流程"等。对于这类问题,第一次检索后把结果缓存起来,后续相同或相近的问题直接返回缓存结果,可以节省向量计算和LLM调用的开销。
3. 第三个优化是文档分块大小的调优。最初设置的是每块1000字符,发现有些块太大,包含的信息太杂,检索精度不够。调整为500字符后,每个块的语义更加聚焦,检索准确率提升了大约15%。
4. 第四个优化是Redis连接池的使用。早期每次检索都创建新的Redis连接,在高并发时会有连接数过多的问题。改用连接池后,连接复用率提高,系统能够支撑的并发量提升了3倍。

# 10. 后续优化方向

虽然当前的知识库系统已经能够满足基本需求,但是还有不少可以改进的地方。

1. 第一个方向是支持更多文档格式。当前只支持PDF,但企业里还有很多Word、Excel、PPT等格式的文档。未来可以集成相应的文档处理库,让知识库能够处理更多类型的文件。
2. 第二个方向是实现文档的增量更新和版本管理。当前是简单的全量替换,缺少版本管理能力。可以为每个文档维护版本历史,用户可以查看文档的更新记录,甚至可以回退到某个历史版本。
3. 第三个方向是引入文档分类和标签。随着文档数量增加,可以按照文档类型(制度、流程、手册等)进行分类,或者添加标签,这样检索时可以先缩小范围,提高精度。
4. 第五个方向是知识图谱的构建。对于结构化的信息,比如审批流程、组织架构,可以构建知识图谱,让AI能够进行更深层次的推理。比如用户问"我要请5天假,需要哪些人审批",AI不仅能从文档找到审批规则,还能结合组织架构找到具体的审批人。
