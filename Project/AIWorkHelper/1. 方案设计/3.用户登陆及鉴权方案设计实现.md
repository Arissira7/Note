# 整体架构设计

权限系统是整个后题系统功能实现的基础也是最核心的问题之一，由于系统提供了两种通信方式——HTTP REST API和WebSocket实时通信，所以需要设计一套统一且高效的鉴权机制，既要保证安全性，又不能因为频繁的认证校验影响用户体验。在技术选型上最终选择了JWT(JSON Web Token)作为鉴权方案的核心。这个决定主要基于以下几点考虑：

1. **无状态化设计** - JWT自包含用户信息，服务端无需维护Session存储，天然适合分布式架构
2. **跨协议复用** - 同一个Token可以在HTTP和WebSocket中使用，降低了实现复杂度
3. **性能优势** - Token验证只需要本地计算签名，无需查询数据库，响应速度更快
4. **前后端分离友好** - Token可以方便地在请求头、URL参数等多种方式传递

系统的鉴权架构采用了分层设计思想，从底层到上层分别是：Token生成与解析层、中间件拦截层、业务逻辑层。各层职责清晰，相互配合形成完整的鉴权链路。

从上面这张架构图可以看出，整个系统的认证流程是这样的：用户首次访问时通过登录接口获取Token，登录过程中会验证用户名和密码，密码验证通过后系统签发一个JWT Token返回给客户端。客户端拿到Token之后，后续的所有请求都会携带这个Token，HTTP请求通过Authorization Header携带，WebSocket连接则可以通过自定义Header或者URL参数传递。服务端在接收到请求时，会在认证拦截层对Token进行校验，校验通过后提取出用户ID并注入到请求上下文中，业务逻辑层就可以直接从上下文获取当前用户信息了。

# **Token机制设计**

JWT Token的设计是整个鉴权方案的基石。在实现Token模块时，主要考虑了三个方面的问题：Token里应该放什么信息、Token的有效期应该怎么设置、以及Token应该怎么传递。

### **Token的生成**

关于Token的`payload`设计，采用比较精简的策略，只在claims里放了三个字段：用户ID、签发时间和过期时间。没有放太多信息是出于安全和性能的考虑。一方面JWT是Base64编码的，并不加密，放太多敏感信息有泄露风险;另一方面Token每次请求都要传输，体积越小网络开销越小。

用户ID用一个自定义的key“aiworkhelper”。其实这个字段可以随意选择。Token生成的核心代码如下：

```go
func GetJwtToken(secretKey string， iat， seconds int64， uid string) (string， error) {
    claims ：= make(jwt.MapClaims)
    claims["exp"] = iat + seconds    // 过期时间
    claims["iat"] = iat               // 签发时间
    claims["aiworkhelper"] = uid      // 用户ID(自定义字段)

    token ：= jwt.New(jwt.SigningMethodHS256)
    token.Claims = claims
    return token.SignedString([]byte(secretKey))
}
```

调用方只需要传入密钥、签发时间、有效期和用户ID四个参数，就能得到一个签名后的JWT Token

### **Token的解析与验证**

Token解析器提供了分层的API设计。最基础的是ParseToken方法，只负责验证Token的签名和有效期。在这个基础上，还封装了ParseWithContext方法，它在解析Token后会将用户信息注入到HTTP请求的Context中。这里有个细节处理，会过滤掉JWT的标准字段(like aud、exp、iss这些)，只注入自定义字段，避免Context里塞太多用不到的东西

```go
ctx ：= r.Context()
for k， v ：= range claims {
    switch k {
    case "aud"， "exp"， "jti"， "iat"， "iss"， "nbf"， "sub"：
        // 忽略JWT标准声明，不注入Context
    default：
        ctx = context.WithValue(ctx， k， v)  // 只注入自定义字段
    }
}
```

业务层要获取用户ID的时候，只需要调用token.GetUId(ctx)这个工具函数，传入当前的Context就能拿到，非常简洁

### Token的传递与过期设计

Token有效期的设计是安全性和用户体验之间的权衡。设置得太短，用户频繁掉线体验不好;设置得太长，Token泄露的风险窗口就变大了。这里把过期时间做成了可配置项，在开发环境可以设置得长一些方便调试，生产环境建议设置成1到2小时。

# HTTP接口鉴权实现

HTTP接口的鉴权是通过Gin中间件来实现的。中间件这个设计模式在Web开发里非常常见，它的好处是可以把一些横切关注点从业务逻辑中剥离出来。对于鉴权这种几乎每个接口都需要的功能来说，用中间件实现比较合适。

JWT中间件的核心逻辑其实很简单，就是从HTTP请求中提取Token，验证签名和有效期，然后把用户信息注入到Context里。整个过程遵循"验证-注入-放行"的流程：

```go
func (m *Jwt) Handler(ctx *gin.Context) {
    // 解析Token并注入用户信息到请求上下文
    r， err ：= m.tokenParser.ParseWithContext(ctx.Request)
    if err != nil {
        httpx.FailWithErr(ctx， err)
        ctx.Abort()  // Token验证失败，中断后续处理
        return
    }

    ctx.Request = r
    ctx.Next()  // 验证成功，继续执行后续Handler
}
```

如果Token验证失败，中间件会调用Abort方法中断后续的处理链，直接返回401错误;如果验证成功，就调用Next方法让请求继续往下走。这种设计保证了只有携带有效Token的请求才能进入业务逻辑层。

在路由注册的时候，这里采用了分组的方式来管理需要鉴权和不需要鉴权的接口：

```go
func (h *User) InitRegister(engine *gin.Engine) {
    // 无需鉴权的路由组
    g0 ：= engine.Group("v1/user")
    g0.POST("/login"， h.Login)

    // 需要鉴权的路由组(注册了JWT中间件)
    g1 ：= engine.Group("v1/user"， h.svcCtx.Jwt.Handler)
    g1.GET("/：id"， h.Info)
    g1.POST(""， h.Create)
    g1.PUT(""， h.Edit)
}
```

通过路由分组，可以很清晰地看出哪些接口是公开的，哪些接口需要登录后才能访问。这种方式也让新增接口的时候不容易出错，开发人员只需要选择合适的路由组就行了，不用在每个Handler里单独处理认证逻辑。

# WebSocket连接鉴权实现

WebSocket的鉴权相比HTTP要复杂一些，因为WebSocket是一个长连接的协议。HTTP每次请求都是独立的，每次都验证Token就行了;但WebSocket建立连接之后，这个连接可能会保持几个小时甚至更长时间，不可能每条消息都重新验证一遍Token，那样性能开销太大了。所以WebSocket的鉴权策略是：在连接建立的握手阶段进行一次完整的Token验证，验证通过后在整个连接的生命周期内都认为用户身份是有效的。

## 握手阶段的认证

具体实现上，WebSocket Server在收到连接请求时，会先调用auth方法进行身份验证。这个验证过程和HTTP中间件类似，也是提取Token、验证签名、提取用户ID。但是有一点不同，WebSocket的Token可以从多个地方获取：

```go
func (s *Ws) auth(r *http.Request) (uid string， tokenStr string， err error) {
    // 优先从自定义Header获取
    tok ：= r.Header.Get("websocket")

    // 兼容从URL参数获取
    if tok == "" {
        tok = r.URL.Query().Get("token")
    }

    if tok == "" {
        return ""， ""， errors.New("没有登入，不存在访问权限")
    }

    // 解析Token获取用户ID
    claims， tokenStr， err ：= s.tokenParser.ParseToken(tok)
    if err != nil {
        return ""， ""， err
    }

    return claims[token.Identify].(string)， tokenStr， nil
}
```

这种降级机制是为了兼容不同的客户端实现，有些WebSocket库设置自定义Header不太方便，通过URL传Token就简单多了。

## 连接管理与双向映射

Token验证通过之后，系统会将HTTP连接升级为WebSocket连接，然后把这个连接和用户ID建立映射关系。这里设计了一个双向映射的数据结构：

```go
type Ws struct {
    uidToConn map[string]*websocket.Conn  // 用户ID -> 连接
    ConnToUid map[*websocket.Conn]string  // 连接 -> 用户ID
    sync.RWMutex
}
```

这里为什么要双向映射呢?因为有两种场景需要快速查找。第一种是服务端要给某个用户主动推送消息，比如AI处理完一个任务需要通知用户，这时候需要根据用户ID找到对应的连接;第二种是连接断开的时候需要清理资源，这时候需要根据连接找到用户ID，然后从两个map里都删除掉。双向映射让这两种查找都是O(1)的时间复杂度。

连接管理还有一个细节是单点登录的实现：

```go
func (s *Ws) addConn(conn *websocket.Conn， uid string) {
    s.RWMutex.Lock()
    defer s.RWMutex.Unlock()

    // 如果用户已有连接，关闭旧连接(实现单点登录)
    if c ：= s.uidToConn[uid]; c != nil {
        c.Close()
    }

    s.uidToConn[uid] = conn
    s.ConnToUid[conn] = uid
}
```

当用户建立新的WebSocket连接时，系统会检查这个用户是不是已经有一个连接了，如果有就把旧连接关闭掉。这样保证了一个用户在同一时刻只能有一个WebSocket连接，实现了"挤下线"的效果。

并发安全也是WebSocket连接管理必须考虑的问题。因为WebSocket Server是高并发的，可能同时有很多goroutine在读写连接映射表，如果不加保护就会出现数据竞争。这里使用了读写锁来保护这两个map，添加和删除连接时用写锁，发送消息时用读锁。读写锁的好处是允许多个goroutine并发读，只有在写的时候才需要独占，这样在读多写少的场景下性能会好很多。

# 用户登录流程设计

用户登录是整个鉴权体系的入口，这个流程的安全性直接关系到整个系统的安全性。登录流程看起来很简单，就是验证用户名和密码，但实际实现时有很多安全细节需要考虑。

## **密码安全**

密码的存储和验证是登录流程中最关键的环节。这里选择了bcrypt作为密码加密算法，而不是常见的MD5或者SHA系列。这个选择主要是基于安全性的考虑。MD5和SHA虽然也是单向哈希，但是它们的设计目标是快速计算，这对于密码加密来说反而是个劣势，因为攻击者可以用很高的速度进行暴力破解。

bcrypt的设计思路正好相反，它故意做得很慢，而且可以通过调整cost参数来控制计算复杂度。加密和验证的代码非常简洁：

```go
// 加密密码
func GenPasswordHash(password []byte) ([]byte， error) {
    return bcrypt.GenerateFromPassword(password， bcrypt.DefaultCost)
}

// 验证密码
func ValidatePasswordHash(password string， hashed string) bool {
    if err ：= bcrypt.CompareHashAndPassword([]byte(hashed)， []byte(password)); err != nil {
        return false
    }
    return true
}
```

bcrypt还有个好处是自动处理盐值，每次加密都会生成随机盐值并附加在hash结果里，验证的时候自动提取，开发者不用手动管理盐值。

## **登录响应设计**

登录成功后返回的数据结构也有讲究。除了返回Token本身，这里还返回了用户ID、用户名和Token过期时间。用户ID和用户名可以让前端在本地缓存一些用户信息，避免频繁请求用户详情接口。Token过期时间是一个绝对的Unix时间戳，而不是相对的秒数，这样可以避免客户端和服务端时间不同步导致的问题。前端可以定期检查当前时间和过期时间的差值，在Token快要过期的时候提醒用户或者自动刷新Token。

关于登录失败时的错误信息，这里做了一个权衡决策。系统会明确告诉用户是"用户不存在"还是"密码错误"，而不是笼统地返回"用户名或密码错误"。这种做法提升了用户体验，用户能明确知道是哪里出了问题，但也带来了一定的安全风险，就是攻击者可以通过错误信息判断用户名是否存在，从而进行用户名枚举攻击。在实际生产环境中，如果对安全性要求特别高，可以考虑统一返回模糊的错误信息，或者增加登录失败次数限制、验证码等额外的防护措施。

# 完整的认证流程

## HTTP API认证流程

HTTP接口的认证流程是比较标准的中间件模式。客户端在请求Header里携带Token，Gin框架的路由层收到请求后，会先执行注册的中间件。JWT中间件调用Token解析器从Header里提取Token，验证签名和有效期。如果验证失败，中间件直接返回401错误并中止后续处理;如果验证成功，就把用户ID注入到Context里，然后调用Next方法让请求继续往下走。业务Handler从Context里获取用户ID，然后执行具体的业务逻辑，查询数据库，最后返回结果给客户端。

## WebSocket认证流程

WebSocket的认证流程稍微复杂一些，因为要处理长连接的场景。客户端发起WebSocket连接请求时，会在握手阶段携带Token，可以通过自定义Header或者URL参数传递。WebSocket Server收到连接请求后，先调用auth方法进行身份验证，提取Token并验证有效性。如果验证失败，直接拒绝连接;如果验证成功，就将HTTP连接升级为WebSocket连接。

连接升级成功后，系统会调用连接管理器的addConn方法建立用户ID和连接的映射关系。这个过程会先检查该用户是否已经有一个连接了，如果有就关闭旧连接，实现单点登录的效果。然后建立双向映射，方便后续根据用户ID查找连接，或者根据连接查找用户ID。

映射建立完成后，WebSocket Server会启动一个goroutine来处理这个连接的消息收发。这个goroutine会一直运行，循环读取客户端发来的消息，处理完成后返回响应。每次处理消息时，都会创建一个包含用户ID的Context，这样业务逻辑层就能知道是哪个用户发来的消息。当连接断开时，无论是客户端主动断开还是网络异常，系统都会调用closeConn方法清理连接映射，释放资源。

# 安全性保障措施

鉴权方案的安全性是重中之重，这里在设计实现的时候考虑了多个层面的安全防护。

首先是密码存储的安全。系统里从来不存储明文密码，所有密码在写入数据库之前都会经过bcrypt加密。即使是管理员创建用户的接口，传入的密码也会先加密再存储。这样即使数据库被攻破，攻击者拿到的也只是不可逆的hash值，很难还原出原始密码。bcrypt的慢哈希特性让暴力破解的成本非常高，基本上可以认为是不可行的。

其次是Token的防伪造机制。JWT使用HMAC-SHA256算法进行签名，签名密钥只保存在服务端的配置文件里，客户端是拿不到的。每次验证Token的时候，服务端会用密钥重新计算签名，然后和Token里携带的签名进行比对，只有完全一致才认为Token有效。这意味着即使攻击者拿到了一个合法Token，也无法修改里面的内容或者伪造一个新Token，因为没有密钥就算不出正确的签名。

Token的过期时间也是一个重要的安全措施。虽然JWT无法主动让某个Token失效，但通过设置合理的过期时间，可以限制Token被盗用的风险窗口。如果Token被泄露，攻击者只能在有效期内使用，过期之后就自动失效了。在生产环境建议把过期时间设置得短一些，比如1-2小时，这样既能保证用户正常使用期间不会频繁掉线，又能在Token泄露时把影响降到最低。

WebSocket连接管理的并发安全也是一个重要方面。由于WebSocket Server是高并发的，多个goroutine可能同时读写连接映射表，如果不做并发控制就会出现数据竞争，导致程序崩溃或者数据错乱。这里使用了读写互斥锁来保护这些共享数据结构，添加和删除连接时使用写锁，查询连接时使用读锁。读写锁允许多个goroutine并发读，只有写的时候才需要独占，在读多写少的场景下能提供更好的性能。

# 配置管理策略

鉴权相关的配置项都是比较敏感的，特别是JWT的签名密钥，如果泄露的话整个鉴权体系就形同虚设了。所以配置管理也是方案设计的重要一环。

这里把JWT相关的配置都放在了独立的配置文件里：

```go
Jwt：
  Secret： "your-secret-key"    # 签名密钥
  Expire： 7200                  # 过期时间(秒)
```

这样做的好处是配置和代码分离，不同环境可以使用不同的配置。测试环境可以用一个简单的密钥，Token过期时间设置得长一些方便调试;生产环境则必须使用强密钥，Token过期时间也要设置得更合理。通过配置文件管理这些参数，修改配置不需要重新编译代码，只要重启服务就行了。

关于签名密钥的安全管理，这里给出的建议是：首先密钥长度至少要32字节以上，使用真随机数生成器生成，不要用生日、公司名称这种可预测的字符串;其次密钥不要硬编码在代码里，也不要提交到代码仓库，最好通过环境变量或者密钥管理服务来注入;最后如果条件允许，可以定期轮换密钥，虽然这会导致旧Token失效，但可以进一步提升安全性。

Token过期时间的设置需要在安全性和用户体验之间找平衡。设置得太短，用户频繁掉线体验不好;设置得太长，Token泄露的风险窗口就变大。一般来说，对于Web应用，1-2小时是比较合适的;对于移动应用，可以考虑设置得长一些，比如7天，但要配合Refresh Token机制，这样既能保持用户登录状态，又不会让Access Token的有效期太长。

# 小结

## 优点

回顾整个鉴权方案的设计和实现，有几个方面做得比较好，值得总结一下。

首先是架构的简洁性和一致性。HTTP和WebSocket两种完全不同的协议，使用了同一套Token机制，用户只需要登录一次就能同时使用两种通信方式。这种统一性大大简化了客户端的实现，也降低了系统的维护成本。Token的生成、解析、验证逻辑都集中在独立的package里，不同的认证入口复用同一套代码，保证了行为的一致性。

其次是性能方面的考虑。JWT的无状态特性让Token验证只需要本地计算签名，不需要查询数据库或者Redis，这对于高并发场景非常友好。WebSocket建立连接后，只在握手阶段验证一次Token，后续通信不再重复验证，避免了不必要的性能开销。连接管理使用了读写锁而不是互斥锁，在读多写少的场景下能提供更好的并发性能。

安全性也是这套方案的重点。密码使用bcrypt慢哈希算法，即使数据库泄露也很难被破解。JWT的签名机制防止了Token伪造和篡改。Token的过期时间限制了泄露后的风险窗口。WebSocket的单点登录机制防止了账号共享。这些措施从多个维度保障了系统的安全性。

最后是可扩展性的设计。Token模块是独立的package，可以在不同场景下复用。UserModel使用接口定义，便于测试和替换实现。JWT的claims可以灵活扩展，需要传递更多用户信息时只需要添加字段。配置和代码分离，不同环境可以使用不同的配置。这些设计为系统的未来演进留下了空间。

## 不足

虽然当前的鉴权方案已经能够满足业务需求，在生产环境也运行得比较稳定，但技术方案总是可以持续优化的。基于实际使用的经验和对业务发展的预判，这里认为有几个方向值得在后续版本中考虑。

第一个是Token刷新机制。当前的方案是Token过期后用户需要重新登录，这在有些场景下体验不够好。比如用户正在编辑一个长文档，写了一半Token过期了，突然被踢出去重新登录，编辑的内容可能就丢失了。比较好的做法是实现Refresh Token机制，登录时同时返回一个短期的Access Token和一个长期的Refresh Token。Access Token用于日常的API调用，Refresh Token用于在Access Token快要过期时获取新的Access Token。这样可以在保证安全性的同时，让用户无感知地保持登录状态。

第二个是更细粒度的权限控制。当前的方案只区分了登录和未登录两种状态，没有角色和权限的概念。这对于小型系统来说够用了，但随着业务复杂度的提升，可能需要实现RBAC(基于角色的访问控制)。比如普通用户只能查看和编辑自己的待办事项，部门主管可以查看整个部门的待办事项，系统管理员可以管理所有用户。实现RBAC需要在用户表里增加角色字段，定义角色和权限的映射关系，然后在中间件或者业务层进行权限检查。虽然增加了一些复杂度，但能够满足更复杂的业务场景。

第三个是Token黑名单机制。JWT的一个经典问题是无法主动让某个Token失效，因为验证过程是无状态的，不依赖任何服务端存储。但在实际业务中，有些场景是需要强制让Token失效的，比如用户修改密码后应该让所有旧Token失效，或者发现账号被盗用需要紧急封禁。一个可行的解决方案是引入Token黑名单，用Redis维护一个失效Token的集合，验证Token时先检查是否在黑名单里。这虽然牺牲了一点无状态性，但能够应对特殊场景的需求。
