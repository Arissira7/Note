AIWorkHelper 是一个基于 Go 语言开发的 AI 驱动工作助手应用，集成了 LangChain AI 框架，提供智能聊天路由和多功能业务逻辑处理能力。项目主要为企业办公业场景提供待办管理、审批流程、知识库检索等智能化服务。

# **技术栈总览**

**核心技术:**

- **语言** : Go 1.24.6
- **Web框架** : Gin (HTTP REST API) + Gorilla WebSocket (实时通信)
- **数据库** : MongoDB (主数据存储)，Redis(向量存储)
- **AI/LLM** : LangChain Go ( `github.com/tmc/langchaingo` ) + 阿里云通义千问 (qwen3-max-preview)
- **认证** : JWT Token
- **日志** : 分布式追踪日志 (tlog)

# 项目架构

AIWorkHelper 在架构设计上采用了双服务器并行的方式来解决企业办公场景中的两类核心需求:一类是传统的 CRUD 操作,另一类是需要实时交互的 AI 对话。从技术实现来看,项目通过 main.go 同时启动了两个独立的服务器实例。HTTP REST API 服务器承载了待办管理、审批流程、部门管理等标准业务功能,这些操作天然适合请求-响应模式。而 WebSocket 服务器则专注于处理需要持续连接的场景,比如用户与 AI 的多轮对话、实时消息推送等 。两个服务器虽然独立运行,但共享同一个 ServiceContext 依赖注入容器,这样既保证了资源的统一管理(数据库连接、LLM 客户端等只需初始化一次),又避免了服务间的强耦合。

```text
 ├── goroutine 1: HTTP 服务器 (端口8080)
    │    └── 处理 REST API 请求
    │        - POST /v1/todo (创建待办)
    │        - GET /v1/todo/list (查询待办)
    │        - POST /v1/chat (AI聊天)
    │        - ...
    │
    └── goroutine 2: WebSocket 服务器 (端口9000)
         └── 处理实时聊天
             - 用户上线/下线
             - 私聊消息
             - 群聊消息
```

在分层设计上，AIWorkHelper 是一个三层结构,但最关键的是中间那层 Gin + LangchainGo 框架层,它把上层的业务功能和下层的基础设施连接起来。

![](2026-05-04/1777882224_71da.png)

最上层是业务应用层,包含了八个主要功能模块:知识库、消息总结、用户管理、待办/审批创建、待办/审批查询、部门管理、通用聊天、AI聊天。这些功能本质上是面向企业办公场景的,涵盖了日常工作中最常见的几类需求。

中间层是整个系统的核心,用 Gin 作为 Web 框架,结合 LangchainGo 来处理 AI相关的逻辑。这一层包含了几个关键组件:日志记录负责追踪请求链路,token监听处理认证,错误处理统一管理异常,记忆机制维护对话上下文,Agent 是 LangChain 的执行器,Chain 负责串联调用流程,RAG处理知识库检索增强,JWT 做身份认证。这些组件协同工作,既要处理传统的 HTTP 请求,又要支撑 AI 对话的复杂交互。

底层分成两块:左边是基础服务,包括 redis 做缓存、mongodb 做数据持久化、docker 做容器化部署;右边是大模型层,支持通义千问、ChatGPT、ollama本地模型三种选择,这样设计给了系统比较大的灵活性,可以根据成本和性能需求切换不同的模型。

从通信协议看,有两种协议方式两种方式:http 和 websocket。http 适合处理那些一次性的请求,比如创建待办、查询审批;websocket 则用在需要持续交互的场景,特别是 AI 对话,因为 Agent执行过程可能需要多轮调用,websocket 能保持连接状态,减少握手开销。

这个架构的设计思路很清晰:把 LangChain 的能力作为中间层,向上支撑各种业务功能,向下对接不同的大模型和基础设施。这样做的好处是业务层不用关心具体用的是哪个大模型,也不用关心 Agent是怎么执行的，只需要定义好功能需求,由中间层去协调和编排。同时因为抽象了大模型层,后续如果要切换模型或者同时支持多个模型,改动会集中在底层,不会影响上层业务。

## 模块详解

### main.go (程序入口)

位置: `main.go` 代码量: 仅66行，非常简单!

```go
func main() {
    // 步骤1: 解析命令行参数
    flag.Parse()

    // 步骤2: 加载配置文件 (etc/api.yaml)
    var cfg config.Config
    conf.MustLoad(*configFile, &cfg)

    // 步骤3: 初始化服务上下文 (超级重要!)
    svcContext, err := svc.NewServiceContext(cfg)

    // 步骤4: 启动HTTP服务 (goroutine并发)
    go func() {
        srv := api.NewHandle(svcContext)
        srv.Run()  // 监听8080端口
    }()

    // 步骤5: 启动WebSocket服务 (goroutine并发)
    go func() {
        srv := ws.NewWs(svcContext)
        srv.Run()  // 监听9000端口
    }()

    // 步骤6: 等待两个服务运行
    sw.Wait()
}
```

这个模块是整个项目的核心。在这个模块中有一个非常重要的对象： `ServiceContext` : 依赖注入容器,后面会详细讲。

### ServiceContext (依赖管理中心)

位置: `internal/svc/servicecontext.go` ，非常重要，可以把他想象成一个工具箱,里面装了项目需要的所有工具:

```go
type ServiceContext struct {
    Config config.Config        // 配置信息

    // 数据库
    Mongo *mongo.Database       // MongoDB连接

    // 所有的Model (数据库操作对象)
    UserModel      model.UserModel
    TodoModel      model.TodoModel
    ApprovalModel  model.ApprovalModel
    ChatLogModel   model.ChatLogModel
    // ... 还有更多Model

    // 中间件
    Jwt *middleware.Jwt         // JWT认证

    // AI相关
    LLMs      *openai.LLM       // 大语言模型客户端
    Callbacks callbacks.Handler  // AI调用监控
}
```

这个模块是整个项目的关键。很多新手看到代码时会疑惑:为什么要搞这么一个大对象,把所有依赖都塞进去?直接在需要的地方 new 一个不行吗?答案是不行,至少在生产环境中不行。

想象一下,如果每个 Handler 都自己创建 MongoDB 连接,那一个请求进来就会创建一次连接,一百个并发请求就是一百个连接。数据库连接数很快就会耗尽,系统直接崩溃。ServiceContext 的作用就是在程序启动时初始化一次所有依赖(数据库连接池、LLM 客户端、Model 实例),然后注入到需要的地方。这样不管来多少请求,都复用同一批资源。

另一个好处是测试。有了 ServiceContext,你可以在测试时注入 Mock 对象,而不需要真的连接数据库或调用 LLM。这对于单元测试非常关键。

初始化过程 ( `NewServiceContext` 函数):

```go
1. 连接MongoDB数据库
2. 创建LLM客户端 (连接通义千问)
3. 初始化所有Model实例
4. 创建JWT中间件
5. 创建默认管理员用户 (root/123456)
```

### Handler层

位置: `internal/handler/api/` 和 `internal/handler/ws/`

Handler 层是系统的门面，它的整体设计是:薄薄的一层,只做协议适配,不掺杂任何业务逻辑。HTTP Handler 的职责很清晰:解析 JSON 请求体,验证参数,调用 Logic 层,将结果序列化回 JSON。WebSocket Handler 稍微复杂一点,因为它需要管理长连接,但核心思想是一样的 - 只负责消息的收发和分发,具体怎么处理交给 Logic 层。

为什么要这样设计?想象一下,如果你在 Handler 里写了很多业务逻辑,那么当你想支持新的协议(比如 gRPC)时,所有业务逻辑都要重写一遍。但如果 Handler 只负责协议转换(HTTP/WebSocket → Go 对象),业务逻辑都在 Logic 层,那么新增协议就只是多写一个 Handler,Logic 层完全复用。

比如创建待办:

```go
// 文件: internal/handler/api/todo.go

// 处理 POST /v1/todo 请求
func (h *Todo) Create(ctx *gin.Context) {
    // 步骤1: 接收前端发来的数据
    var req domain.Todo
    if err := httpx.BindAndValidate(ctx, &req); err != nil {
        httpx.FailWithErr(ctx, err)  // 数据格式错误,返回失败
        return
    }

    // 步骤2: 调用Logic层处理业务逻辑
    res, err := h.todo.Create(ctx.Request.Context(), &req)

    // 步骤3: 返回结果给前端
    if err != nil {
        httpx.FailWithErr(ctx, err)  // 失败响应
    } else {
        httpx.OkWithData(ctx, res)    // 成功响应
    }
}
```

### Logic层

位置: `internal/logic/`

Logic 层是整个系统的灵魂,所有业务规则都在这里实现。如果说 Handler 是表面，Model 是底层仓库，那 Logic 就是逻辑大脑。

这一层的代码也是最复杂的，因为它要处理各种业务场景:默认值设置、权限校验、数据转换、状态流转等等。但整体设计上好 Logic 层代码还是比较清晰的。

Logic 层不直接操作数据库,而是通过 Model 层的接口。这样的好处是,即使你把 MongoDB 换成 MySQL,Logic 层的代码一行都不用改,只需要重新实现 Model 层的接口即可。这就是分层架构的价值。

比如创建待办：todo.go，

```go
// 文件: internal/logic/todo.go

// 创建待办的业务逻辑
func (l *todo) Create(ctx context.Context, req *domain.Todo) (*domain.IdResp, error) {
    // 业务规则1: 获取当前用户ID
    uid := token.GetUId(ctx)

    // 业务规则2: 如果没指定执行人,默认是创建人自己
    executes := make([]*model.UserTodo, 0)
    for _, id := range req.ExecuteIds {
        executes = append(executes, &model.UserTodo{
            UserId: id,
            TodoStatus: model.TodoPending,  // 初始状态:待处理
        })
    }

    if len(executes) == 0 {  // 没有执行人
        executes = append(executes, &model.UserTodo{
            UserId: uid,  // 默认是创建人
        })
    }

    // 业务规则3: 调用Model层保存到数据库
    id := primitive.NewObjectID()
    err := l.svcCtx.TodoModel.Insert(ctx, &model.Todo{
        ID:         id,
        CreatorId:  uid,
        Title:      req.Title,
        DeadlineAt: req.DeadlineAt,
        Desc:       req.Desc,
        Executes:   executes,
        TodoStatus: model.TodoPending,
        CreateAt:   time.Now().Unix(),
    })

    // 返回新创建的待办ID
    return &domain.IdResp{Id: id.Hex()}, nil
}
```

Logic层的职责：

1. 实现业务规则 (如默认执行人逻辑)
2. 调用Model层操作数据库
3. 处理数据转换 (domain → model)
4. 不处理HTTP请求! (交给Handler层)
5. 不直接操作数据库! (交给Model层)

### Model层

位置: `internal/model/`

Model 层是数据访问的唯一入口,它封装了所有数据库操作,对外提供统一的接口。这一层的设计理念是:屏蔽底层实现细节,提供业务友好的 API。

比如插入数据时,如果没有 ID 就自动生成一个,自动设置创建时间和更新时间。这些基础数据操作都在 Model 层实现，Logic 层完全不用关心。这样 Logic 层的代码就会很干净,只需要关注业务规则。

另一个重要的设计是接口化。每个 Model 都定义了一个接口(如 TodoModel),然后有一个默认实现(defaultTodoModel)。这样在测试时可以轻松替换成 Mock 实现,不需要真的连接数据库。这对于单元测试非常重要。

每个Model对应一个MongoDB集合 (表):

```go
// 文件: internal/model/todomodel.go

type TodoModel interface {
    Insert(ctx, *Todo) error       // 插入待办
    FindOne(ctx, id string) (*Todo, error)  // 查询单个待办
    Update(ctx, *Todo) error       // 更新待办
    Delete(ctx, id string) error   // 删除待办
    List(ctx, *TodoListReq) ([]*Todo, int64, error)  // 查询列表
}

// 实现: 插入待办
func (m *defaultTodoModel) Insert(ctx context.Context, data *Todo) error {
    // 如果没有ID,自动生成
    if data.ID.IsZero() {
        data.ID = primitive.NewObjectID()
        data.CreateAt = time.Now().Unix()
        data.UpdateAt = time.Now().Unix()
    }

    // 调用MongoDB API插入数据
    _, err := m.col.InsertOne(ctx, data)
    return err
}
```

### AI智能路由（项目亮点）

位置: `pkg/langchain/router/router.go` ，这是项目最复杂的部分。它解决什么问题?

- 用户说"帮我创建明天的待办" → 应该调用待办Handler
- 用户说"提交一个请假审批" → 应该调用审批Handler
- 用户说"公司考勤制度是什么" → 应该调用知识库Handler

传统方法: 写很多 `if-else` 判断关键词 ❌ AI方法: 让大语言模型智能判断!

工作流程:

```text
用户输入: "帮我创建明天的待办:准备会议材料"
    ↓
【步骤1】Router调用LLM分析输入
    LLM返回: {destination: "todo"}
    ↓
【步骤2】Router选择TodoHandler
    ↓
【步骤3】调用TodoHandler.Chains()
    ↓
TodoHandler使用Agent执行工具链:
    - 工具1: TimeParser ("明天" → Unix时间戳)
    - 工具2: TodoAdd (创建待办)
    ↓
返回结果给用户
```

如果说 Router 是"大脑"负责决策,那么这些 Tool 就是"手脚"负责执行。每个 Tool 就像一个技能,Agent 可以根据需要调用它们。

这里有个很重要的设计理念:工具的粒度要合适。太粗了不灵活,太细了又会让 Agent 迷失方向。比如 TimeParser 这个工具,它只做一件事 - 把自然语言时间转成时间戳。它不关心这个时间是用来创建待办还是审批,也不关心后续怎么处理。这样的设计让工具可以被多个 Handler 复用。

另一个值得注意的点是工具的返回值。所有工具都返回字符串,即使是结构化数据也会序列化成 JSON 字符串。这是因为 LLM 只能理解文本,返回字符串可以让 LLM 直接看到工具的输出,从而做出下一步决策。

# 数据库表结构设计

MongoDB作为一个文档型NoSQL数据库,在这个项目中承担了所有业务数据的存储工作。与传统的关系型数据库不同,MongoDB的数据模型更加灵活 - 它不需要预先定义严格的表结构,可以在文档中嵌套子文档和数组,这对于表达复杂的业务关系非常有帮助。

但灵活不代表随意。项目中的每个集合(MongoDB中的"表")都有明确的数据结构定义,通过Go的struct和bson标签来约束。这样既保留了MongoDB的灵活性,又确保了数据的一致性。更重要的是,良好的表结构设计直接影响查询效率和业务扩展能力。

下面我们逐个来看项目中的核心表结构,重点关注每个表的设计思路、字段含义,以及为什么要这样设计。

## 用户表 (user)

用户表是整个系统的基础,所有业务操作都需要关联到具体的用户。这个表的设计相对简单,但有几个值得注意的点。

### 表结构定义

```go
type User struct {

    Name     string             `bson:"name" json:"name"`           // 用户名
    Password string             `bson:"Password" json:"Password"`   // 密码(加密存储)
    Status   int                `bson:"status" json:"status"`       // 用户状态
    IsAdmin  bool               `bson:"isAdmin" json:"isAdmin"`     // 是否管理员
    UpdateAt int64              `bson:"updateAt" json:"updateAt"`   // 更新时间
    CreateAt int64              `bson:"createAt" json:"createAt"`   // 创建时间
}
```

集合名: `user` ，位置: `internal/model/usertypes.go:7`

### 字段说明

|字段名 |类型 |说明 |示例值 |索引 |
|---|---|---|---|---|
|_id |ObjectID |MongoDB主键 |67a1b2c3d4e5f6789abcdef0 |主键 |
|name |string |用户名(唯一) |"张三" |唯一索引 |
|Password |string |加密后的密码 |"$2a$10$..." |- |
|status |int |用户状态 |1=正常, 0=禁用 |- |
|isAdmin |bool |是否管理员 |true/false |- |
|updateAt |int64 |更新时间戳 |1730505600 |- |
|createAt |int64 |创建时间戳 |1730505600 |- |

### 设计要点

1. 用户名作为登录凭证

项目中用户登录使用用户名+密码的方式,因此 `name` 字段需要建立唯一索引。这样做的好处是查询速度快,且保证用户名不重复。但在实际生产环境中,可能还需要支持手机号、邮箱等多种登录方式,这时候可以考虑增加 `phone` 、 `email` 字段,并分别建立唯一索引。

2. 密码存储

密码字段存储的是经过bcrypt加密后的哈希值,而不是明文。bcrypt是一种单向加密算法,即使数据库泄露,攻击者也无法反推出原始密码。每次用户登录时,系统会对输入的密码做同样的加密,然后与数据库中的哈希值比对。

3. 默认管理员

系统启动时会自动创建一个默认管理员账号(root/123456),这是通过 `ServiceContext` 初始化时调用 `FindAdminUser` 检查,如果不存在就创建实现的。管理员账号的 `isAdmin` 字段为true,可以用来做权限控制。

4. 后续可考虑补充字段

当前用户表结构比较简单,在实际业务中可能还需要:

- `phone` : 手机号
- `email` : 邮箱
- `avatar` : 头像URL
- `departmentId` : 所属部门ID
- `position` : 职位

## 待办事项表 (todo)

待办表是项目中最核心的业务表之一,它的设计体现了MongoDB文档型数据库的优势 - 通过嵌套数组来表达一对多关系,避免了传统关系型数据库中需要创建关联表的麻烦。

### 表结构定义

```go
type Todo struct {
    ID         primitive.ObjectID `bson:"_id,omitempty" json:"id,omitempty"`
    CreatorId  string             `bson:"creatorId"`     // 创建人ID
    Title      string             `bson:"title"`         // 待办标题
    DeadlineAt int64              `bson:"deadlineAt"`    // 截止时间
    Desc       string             `bson:"desc"`          // 待办描述

    Executes   []*UserTodo        `bson:"executes"`      // 执行人列表
    TodoStatus TodoStatus         `bson:"todo_status"`   // 待办状态
    UpdateAt   int64              `bson:"updateAt"`      // 更新时间
    CreateAt   int64              `bson:"createAt"`      // 创建时间
}

// 执行人子文档
type UserTodo struct {
```

### 设计要点

1. 嵌套文档 vs 关联表

待办表最大的特点是使用了两个嵌套数组: `executes` (执行人列表)和 `records` (操作记录)。如果用传统的关系型数据库,这需要创建两个关联表:

- `todo_user` 表: 记录待办与执行人的多对多关系
- `todo_record` 表: 记录待办的操作日志

但在MongoDB中,直接用嵌套数组就解决了。这样做的好处是:

- 一次查询就能获取待办及其所有执行人、操作记录
- 不需要做join操作,性能更好
- 数据局部性好,待办相关的所有信息都在一个文档里

缺点是:

- 如果执行人数量特别多(比如超过100人),文档会很大
- 更新执行人状态时需要更新整个文档

但对于待办这种业务场景,执行人一般不会超过10个,所以嵌套文档是更好的选择。

2. 双层状态设计

待办有两层状态:

- `todo_status` : 整个待办的状态(待处理/进行中/已完成/已取消/已超时)
- `executes[].todoStatus` : 每个执行人的完成状态

这样设计是因为一个待办可能有多个执行人,每个人的完成进度可能不同。当所有执行人都完成时,待办的整体状态才会变为"已完成"。这种设计在协作场景中非常常见。

3. 查询优化的索引

注意目前项目内的查询都没有用到索引，这是一个tob的项目，用户量应该不大，目前考虑性能是完全够的，文档中所有的索引优化，都可以认为是后续用户量大了之后的一个优化方向

待办表的查询场景主要有:

- 按用户ID查询:查询某个用户作为执行人的所有待办
- 按时间范围查询:查询某个时间段内的待办

因此需要在 `executes.userId` 和 `create_at` 上建立复合索引:

```js
db.todo.createIndex({"executes.userId": 1, "create_at": -1})
```

这个索引可以高效支持类似这样的查询:

```js
db.todo.find({
  "executes.userId": "67a1b2c3...",
  "create_at": {"$gte": startTime, "$lte": endTime}
}).sort({"create_at": -1})
```

4. 操作记录的冗余设计

`Records` 数组中的 `userName` 字段是一个典型的冗余设计。虽然有 `userId` ,理论上可以通过查询user表获取用户名,但这样会导致查询变得复杂。通过在记录中直接存储用户名,查询待办详情时就不需要再去查user表了。代价是如果用户改名,历史记录中的名字不会同步更新 - 但这通常是可以接受的,因为操作记录反映的是当时的状态。

## 审批单据表 (approval)

### 设计要点

1. 多态字段设计

审批表最特别的地方在于 `MakeCard` 、 `Leave` 、 `GoOut` 三个字段,它们是互斥的 - 一个审批单据只会有其中一个字段有值。这种设计在关系型数据库中通常需要创建子表(如 `approval_leave` 表),但在MongoDB中可以直接用可选字段( `omitempty` )来实现。

当创建一个请假审批时:

```go
approval := &Approval{
    Type: LeaveApproval,
    Leave: &Leave{
        Type: Annual,  // 年假
        StartTime: xxx,
        EndTime: yyy,
    },
    // MakeCard和GoOut都是nil
}
```

这样做的好处是:

- 所有审批都在同一个集合,便于统一查询和统计
- 不需要判断类型后去不同的表查询
- 扩展新的审批类型很简单,加一个新字段即可

2. 审批流程设计

`Approvers` 数组记录了审批流的每一个节点:

```go
Approvers: []*Approver{
    {UserId: "leader1", Status: Pass, Reason: "同意"},    // 第1层:直属领导
    {UserId: "leader2", Status: Processed, Reason: ""}, // 第2层:部门总监(当前节点)
    {UserId: "leader3", Status: Notstarted, Reason:""}, // 第3层:CEO(未到达)
}
```

`ApprovalIdx` 字段指向当前审批节点的索引(从0开始), `ApprovalId` 是当前审批人的ID。当一个审批人通过后,系统会:

1. 更新 `Approvers[ApprovalIdx].Status = Pass`
2. `ApprovalIdx++` 移动到下一个节点
3. 更新 `ApprovalId` 为下一个审批人的ID

如果所有审批人都通过, `Status` 字段会变为 `Pass` (通过), `FinishAt` 记录完成时间。

1. 统计优化字段

`FinishDay` 、 `FinishMonth` 、 `FinishYeas` 这三个字段看起来是冗余的(因为可以从 `FinishAt` 时间戳计算出来),但它们的存在是为了方便统计查询。

比如要统计"2025年11月完成的审批数量":

```js
// 有冗余字段
db.approval.countDocuments({finishMonth: 202511})

// 没有冗余字段(需要时间范围查询)
db.approval.countDocuments({
  finishAt: {$gte: start, $lte: end}
})
```

前者可以利用索引更高效,查询语句也更简洁。这是一种典型的用空间换时间的优化策略。

2. 查询索引建议

审批表的常见查询场景:

- 查询我提交的审批: `{userId: "xxx"}`
- 查询待我审批的: `{approvalId: "xxx", status: 1}`
- 按时间统计: `{finishMonth: 202511}`

建议建立以下索引:

```js
db.approval.createIndex({userId: 1, createAt: -1})
db.approval.createIndex({approvalId: 1, status: 1})
db.approval.createIndex({finishMonth: 1})
```

## 部门表 (department)

```go
    Count      int64              `bson:"count"`      // 部门人数
    UpdateAt   int64              `bson:"updateAt"`
    CreateAt   int64              `bson:"createAt"`
}
```

集合名: `department` ， 位置: `internal/model/departmenttypes.go:9`

### 字段说明

|字段名 |类型 |说明 |示例值 |
|---|---|---|---|
|_id |ObjectID |MongoDB主键 |67a1b2c3... |
|name |string |部门名称 |"技术部" |
|parentId |string |父部门ID |"67a1b2..." (空表示顶层) |
|parentPath |string |祖先路径 |":rootId:parentId:" |

### 设计要点

1. 物化路径模式

`parentPath` 字段存储了从根节点到当前节点父节点的完整路径,用冒号分隔:

```text
根部门(公司):
  _id: "root"
  parentPath: ""
  level: 0

一级部门(技术部):
  _id: "tech"
  parentId: "root"
  parentPath: ":root:"
  level: 1

二级部门(前端组):
  _id: "frontend"
  parentId: "tech"
  parentPath: ":root:tech:"
  level: 2

三级部门(React小组):
  _id: "react"
  parentId: "frontend"
  parentPath: ":root:tech:frontend:"
  level: 3
```

这种设计的好处是查询某个部门的所有子孙部门(包括子部门、孙部门等):

```js
// 查询技术部下的所有部门
db.department.find({
  parentPath: {$regex: /^:root:tech:/}
})
```

查询某个部门的祖先链:

```go
// 解析parentPath
ancestors := ParseParentPath(dept.ParentPath)
// 返回: ["root", "tech", "frontend"]
```

如果不用物化路径,而是只存储 `parentId` ,要查询所有子孙部门就需要递归查询,性能会很差。

2. 层级字段的作用

`level` 字段记录了部门的层级深度,主要用于:

- 控制组织架构的最大深度(比如最多5级)
- 按层级查询(如查询所有一级部门)
- UI展示时的缩进计算

1. 人数统计字段

`count` 字段是一个聚合统计字段,记录该部门的人数。这个值需要在用户加入/离开部门时更新。虽然也可以通过查询user_department关联表来实时统计,但存储一个冗余字段可以避免频繁的关联查询。

3. 缺少的字段

当前的部门表结构比较简单,在实际业务中可能还需要:

- `description` : 部门描述/职责
- `status` : 部门状态(正常/撤销/合并)
- `sort` : 排序字段(同级部门的显示顺序)

## 聊天记录表 (chat_log)

聊天记录表用于存储所有的聊天消息,包括群聊和私聊。由于聊天记录的数据量会非常大,且主要是追加写入,很少修改,因此在设计上需要特别注意查询效率。

### 表结构定义

```go
type ChatLog struct {
    ID primitive.ObjectID `bson:"_id,omitempty"`

    ConversationId string   `bson:"conversationId"` // 会话ID
    SendId         string   `bson:"sendId"`         // 发送者ID
    RecvId         string   `bson:"recvId"`         // 接收者ID(群聊为空)
    ChatType       ChatType `bson:"chatType"`       // 聊天类型
    MsgContent     string   `bson:"msgContent"`     // 消息内容
    SendTime       int64    `bson:"sendTime"`       // 发送时间戳

    UpdateAt int64 `bson:"updateAt"`
    CreateAt int64 `bson:"createAt"`
}

// 聊天类型枚举
type ChatType int
const (
    GroupChatType  ChatType = 1 // 群聊
    SingleChatType ChatType = 2 // 私聊
)
```

集合名: `chat_log` ，位置: `internal/model/chatlogtypes.go:16`

### 字段说明

|字段名 |类型 |说明 |示例值 |索引 |
|---|---|---|---|---|
|_id |ObjectID |MongoDB主键 |67a1b2c3... |主键 |
|conversationId |string |会话唯一标识 |"all"(群聊)或"uid1_uid2" |复合索引 |
|sendId |string |发送者用户ID |"67a1b2..." |- |
|recvId |string |接收者用户ID |"67a1b2..."(私聊),空(群聊) |- |
|chatType |int |1=群聊, 2=私聊 |1 或 2 |- |
|msgContent |string |消息内容 |"你好,明天开会" |- |
|sendTime |int64 |发送时间戳 |1730505600 |复合索引 |

### 设计要点

1. 会话ID的设计

`conversationId` 是聊天记录的核心字段,它的值取决于聊天类型:

群聊:

```go
conversationId = "all"  // 固定值,所有人的群聊在一个会话里
```

私聊:

```go
// 两个用户ID排序后用下划线连接
uid1, uid2 := "user_A", "user_B"
if uid1 > uid2 {
    uid1, uid2 = uid2, uid1  // 保证顺序一致
}
conversationId = uid1 + "_" + uid2  // "user_A_user_B"
```

这样设计的好处是:

- 同一个会话的所有消息有相同的 `conversationId`
- 查询会话历史只需要一个条件: `{conversationId: "xxx"}`
- 私聊的会话ID是确定的,不需要额外维护会话表

2. 时间范围查询优化

聊天记录最常见的查询是"获取某个会话在某个时间范围内的消息":

```js
db.chat_log.find({
  conversationId: "all",
  sendTime: {$gte: startTime, $lte: endTime}
}).sort({sendTime: 1})
```

为了优化这种查询,需要建立复合索引:

```js
db.chat_log.createIndex({conversationId: 1, sendTime: 1})
```

这个索引可以高效支持:

- 按会话ID过滤
- 按时间范围过滤
- 按时间排序

3. 数据增长与分片

聊天记录是增长最快的表,在大规模应用中可能每天产生数百万条记录。当数据量达到一定规模后,需要考虑:

按时间分表/分片:

```text
chat_log_202501  // 2025年1月的消息
chat_log_202502  // 2025年2月的消息
...
```

TTL索引(Time To Live):

```js
// 自动删除180天前的消息
db.chat_log.createIndex(
  {createAt: 1},
  {expireAfterSeconds: 180*24*3600}
)
```

4. AI总结功能的支持

项目中有一个"聊天记录总结"功能,它需要查询某个时间段的聊天记录,然后喂给LLM生成摘要。对应的查询方法是:

```go
func (m *ChatLogModel) ListBySendTime(
    ctx context.Context,
    conversationId string,
    sendStartTime, sendEndTime int64,
) ([]*ChatLog, error)
```

这个方法的实现就是用上面提到的复合索引来查询。返回的消息列表会按 `sendTime` 升序排列,保证时间顺序正确。

## 表关系总结

虽然MongoDB是NoSQL数据库,不强制外键关系,但表之间仍然存在逻辑关联:

```text
User (用户)
  ├─→ Todo.CreatorId (创建的待办)
  ├─→ Todo.Executes[].UserId (执行的待办)
  ├─→ Approval.UserId (提交的审批)
  ├─→ Approval.Approvers[].UserId (审批节点)
  ├─→ ChatLog.SendId / RecvId (发送/接收的消息)
  └─→ Department.LeaderId (负责的部门)

Department (部门)
  └─→ Department.ParentId (父部门,自关联)

Todo (待办)
  ├─→ User.ID (创建人)
  └─→ User.ID (执行人,通过Executes数组)

Approval (审批)
  ├─→ User.ID (申请人)
  └─→ User.ID (审批人,通过Approvers数组)

ChatLog (聊天)
  ├─→ User.ID (发送者)
  └─→ User.ID (接收者)
```
