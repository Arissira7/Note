AI聊天助手不仅仅是一个能聊天的AI，而是一个能够真正理解用户意图、能调用业务系统、能完成实际工作的智能助手。基于这个思路，这里设计了一套"智能路由+专业处理器+工具调用"的三层架构。核心理念很简单:让AI不仅能理解用户在说什么，还能知道该找谁去做，以及怎么做。

在技术选型上，选择了LangChain作为AI能力的技术基座。这个决策主要基于几个考虑:首先LangChain提供了完善的链式调用和记忆机制，这对于构建有上下文理解能力的对话系统至关重要;其次它的Agent和Tools体系让我们可以很方便地把AI能力和业务逻辑连接起来;最重要的是，LangChain的抽象层设计得很好，让我们可以专注于业务逻辑的实现，而不用过多关心底层的模型调用细节。

当然，引入LangChain也带来了新的挑战。如何设计路由策略让AI能准确选择合适的处理器?如何管理不同用户的对话上下文?如何保证工具调用的安全性和可靠性?这些问题在后面的章节里会详细阐述解决方案。

# 1. 整体架构设计

AI助手聊天服务的架构设计遵循了"分层解耦、职责单一"的原则。整个系统分为路由层、处理器层、工具层三个核心层次，每一层都有明确的职责边界，层与层之间通过标准接口通信。这种设计的好处是扩展性强，比如要新增一个"会议管理"功能，只需要实现一个新的处理器和对应的工具集，不需要改动核心路由逻辑。

![BlockNote image](https://ls8sck0zrg.feishu.cn/space/api/box/stream/download/asynccode/?code=MTA5OTMyZGMyZWE0YTdkYjc2NzczN2M5NzFmMmNhYTBfNzkyd2w5eEsyQmJSRnZiTk5seTZQMnlvUmRDVVRIU21fVG9rZW46RTNrZ2JGc2s4b1k1dE14MGo3Q2NqVTlsbkZoXzE3Nzc4MzY2MjE6MTc3Nzg0MDIyMV9WNA)

从这张架构图可以看出，整个AI助手聊天服务的核心是智能路由器。当用户发送一条消息时，路由器会调用LLM分析这条消息的意图，然后根据分析结果选择最合适的处理器。每个处理器都专注于特定领域的任务，比如TodoHandle负责所有待办相关的操作，ApprovalHandle处理审批流程，Knowledge负责知识库的查询和更新。如果用户的问题不属于任何专业领域，比如闲聊或者通用问答，就会交给默认处理器来处理。

这套架构有几个关键的设计亮点。第一是路由决策的智能化，我们不是用关键词匹配这种简单粗暴的方式，而是让LLM真正理解用户的意图。比如用户说"明天下午3点前要完成那个报告"，路由器能够识别出这是创建待办的需求，即使句子里没有出现"待办"这个词。第二是处理器的插件化设计，每个处理器都实现了统一的Handler接口，新增处理器就像插拔USB设备一样简单。第三是工具的可组合性，不同处理器可以共享基础工具，比如UserList和TimeParser是所有处理器都可能用到的。

记忆管理层是另一个重要的设计。这里实现了多会话隔离的记忆机制，每个用户的对话历史都单独存储，互不干扰。这样用户A和AI聊到一半，切换到别的页面，稍后回来继续聊时，AI还能记得之前的上下文。而且记忆不仅仅是简单地存储对话，我们还实现了摘要机制，当对话历史太长时会自动总结，既节省了Token消耗，又保留了关键信息。

# 2. 智能路由系统设计

智能路由系统是整个AI助手的大脑，它的职责是理解用户意图并做出正确的分发决策。在设计这个系统时，面临的最大挑战是:如何让路由既准确又高效?准确性要求路由器能够正确识别用户的真实需求，不能把"查询待办"误判为"创建待办";高效性要求路由决策的时间要短，用户不能等太久。

## 2.1 路由决策流程

路由器的决策过程可以分为四个关键步骤:上下文加载、意图分析、处理器选择、结果执行。整个流程既保证了决策的准确性，又通过多层降级策略确保了系统的可靠性。

![BlockNote image](https://ls8sck0zrg.feishu.cn/space/api/box/stream/download/asynccode/?code=NWUzOGJmMDNkZGNkMjgzMThhMGQ4ZmNiNmQ0NTE5OTRfaFNTeXgxa2V0QXZicGJFMUpHcGw4UGFndWFmc1JJWkdfVG9rZW46SGpFMmJoU3Jpb01ycjZ4NXk2aGNJUVdkbjZkXzE3Nzc4MzY2MjE6MTc3Nzg0MDIyMV9WNA)

从这个流程图可以看出，路由决策的核心是LLM分析环节。路由器会把用户的当前输入、完整的对话历史、以及所有可用处理器的描述组装成一个提示词，发送给大模型。LLM会基于这些信息做出判断，返回最合适的处理器名称。这种设计的巧妙之处在于，我们完全依赖LLM的理解能力来做意图识别，而不是编写复杂的规则或者训练分类模型。

传统的意图识别通常有两种方案:关键词匹配和分类模型。关键词匹配太僵硬，比如用户说"明天下午3点前要完成那个报告"，这句话里根本没有"待办"这个词，关键词匹配就会失效。分类模型虽然准确性更高，但需要大量标注数据，而且每次新增处理器都要重新训练模型，维护成本很高。

而我们的方案不需要任何标注数据，也不需要训练。只要为每个处理器写好Name和Description，LLM就能根据这些描述做出合理的判断。更重要的是，这个方案天然支持扩展，新增处理器只需要在注册列表里加一行代码，路由逻辑完全不用改动。

## 2.2 处理器注册机制

每个处理器都需要实现Handler接口，这个接口定义了三个方法:Name()返回处理器的唯一标识，Description()返回处理器的功能描述，Chains()返回实际执行逻辑的LangChain链。路由器在初始化时会收集所有处理器的Name和Description，然后生成一个提示词模板，告诉LLM有哪些处理器可用，每个处理器能做什么。

```go
func NewChat(svc *svc.ServiceContext) Chat {
    // 初始化所有专业处理器
    handlers := []router.Handler{
        chatinternal.NewTodoHandle(svc)，     // 待办事项处理器
        chatinternal.NewKnowledge(svc)，      // 知识库处理器
        chatinternal.NewApprovalHandle(svc)， // 审批处理器
        chatinternal.NewChatLogHandle(svc)，  // 聊天记录处理器
    }

    // 创建多会话内存管理器
    memory := memoryx.NewMemoryx(func() schema.Memory {
        return memoryx.NewSummaryBuffer(svc.LLMs， 50，
            memoryx.WithCallback(svc.Callbacks)，
            memoryx.WithOutParser(memoryOutput))
    })

    return &chat{
        memory: memory，
        svc:    svc，
        router: router.NewRouter(svc.LLMs， handlers，
            router.WithMemory(memory)，
            router.Withcallback(svc.Callbacks)，
            router.WithEmptyHandler(chatinternal.NewDefaultHandler(svc))，
        )，
    }
}
```

这种注册机制的好处是扩展性极强。比如未来要增加一个"会议管理"功能，这里只需要实现一个MeetingHandle，然后在NewChat方法里把它加到handlers列表中就行了，完全不需要修改路由器的代码。而且处理器之间是完全解耦的，TodoHandle的实现不会影响到ApprovalHandle，每个团队成员可以独立开发各自负责的处理器。

## 2.3 降级策略设计

路由系统的可靠性也是重点考虑的问题。万一LLM返回了一个不存在的处理器名称怎么办?万一LLM的输出格式不对，解析失败怎么办?为了应对这些异常情况，需要设计多层降级策略。

第一层降级是默认处理器。如果路由器发现选中的处理器不存在，或者根本没有选中任何处理器，就会自动把请求转给DefaultHandler。DefaultHandler是一个通用的对话处理器，它不调用任何工具，只是用LLM进行普通的对话，这样至少能保证用户得到一个有意义的回复。

第二层降级是错误处理。在调用处理器的过程中，可能会遇到各种异常，比如工具调用失败、数据库连接超时等。这里是在在AIChat方法里加了特殊的错误处理逻辑，如果是Agent输出解析错误，会尝试从错误信息中提取有用的内容返回给用户，而不是直接抛出异常。

```go
func (l *chat) aiService(ctx context.Context， req *domain.ChatReq) (resp *domain.ChatResp， err error) {
    v， err := chains.Call(ctx， l.router， map[string]any{
        langchain.Input: req.Prompts，
    }， chains.WithCallback(l.svc.Callbacks))

    if err != nil {
        // 特殊处理Agent输出解析错误
        if strings.Contains(err.Error()， "unable to parse agent output") {
            parts := strings.Split(err.Error()， ": ")
            if len(parts) > 1 {
                content := parts[len(parts)-1]
                return &domain.ChatResp{
                    ChatType: domain.DefaultHandler，
                    Data:     content，
                }， nil
            }
        }
        return nil， err
    }

    // 正常处理输出...
}
```

这种多层保护的设计让系统具有很好的鲁棒性。即使某个环节出了问题，用户也能得到一个合理的响应，而不是系统崩溃或者返回一堆技术错误信息。

# 3. Agent设计

Agent是整个AI助手系统最核心的组件，它让AI真正具备了自主完成任务的能力。在设计Agent时，最大的挑战是:如何让LLM不仅理解用户要什么，还能自己规划步骤、选择工具、执行操作，最终完成任务?这需要Agent具备推理能力、规划能力和执行能

## 3.1 Agent执行循环机制

Agent的工作方式不是一次性的，而是一个"思考-行动-观察"的循环过程。这个循环会持续进行，直到任务完成或达到最大步数限制。这里采用的是ReAct(Reasoning and Acting)模式，这是目前最有效的Agent实现范式之一。

这里以一个AI创建待办事项的事件来看下Agent的执行循环机制

![BlockNote image](https://ls8sck0zrg.feishu.cn/space/api/box/stream/download/asynccode/?code=ZGJhMmFhYmQ1ZjMyZjE3OTY1MjU4NDQzOTliY2RlZDNfclVwRklrMWpKdzZEUE9nSXJET09ibXBKWEEwcGM3VGZfVG9rZW46SjgwSWI0QzBxbzVyTG94ZjRIOWM5WkxqbjhiXzE3Nzc4MzY2MjE6MTc3Nzg0MDIyMV9WNA)

从这个时序图可以清楚地看到，Agent完成一个创建待办的任务经历了四轮思考-行动-观察的循环。每一轮循环，LLM都会基于当前掌握的信息做出判断:我现在知道了什么?还缺什么?下一步应该做什么?这种自主推理的能力正是Agent的核心价值。

在第一轮循环中，LLM分析用户输入后发现用户提到的是"王员工"这个人名，但系统需要的是用户ID，所以决定先调用user_list工具进行查询。工具返回结果后，Agent把这个结果作为"观察"记录下来，进入下一轮循环。

第二轮循环中，LLM发现还需要处理时间信息，"明天下午3点"是自然语言表达，需要转换为系统能理解的Unix时间戳，于是调用time_parser工具。这个决策完全是LLM自主做出的，我们没有编写任何调度逻辑。

第三轮循环中，所有必要的信息都已经准备好了:用户ID、时间戳、待办标题，LLM判断可以调用todo_add工具来创建待办了。工具执行成功后返回创建的待办ID。

第四轮循环中，LLM分析发现任务已经完成，不需要再调用其他工具，于是生成最终答案并结束循环。

## 3.2 Agent提示词工程

Agent能够正确推理和行动，很大程度上依赖于提示词的设计。使用的是MRKL(Modular Reasoning， Knowledge and Language)提示词模板，这个模板明确告诉LLM它的角色、可用的工具、以及应该如何思考和行动。

提示词的结构大致是这样的:

```text
你是一个AI助手，可以使用以下工具来帮助用户:

工具列表:
1. user_list: 根据用户名查询用户ID
   输入: 用户姓名
   输出: 用户ID列表

2. time_parser: 将自然语言时间转换为Unix时间戳
   输入: 时间描述(如"明天下午3点")
   输出: Unix时间戳

3. todo_add: 创建待办事项
   输入: {"title": "标题"， "deadlineAt": 时间戳， "executeIds": ["用户ID"]}
   输出: 创建的待办ID

使用以下格式进行思考和行动:

Thought: 我需要思考应该做什么
Action: 要使用的工具名称
Action Input: 工具的输入参数
Observation: 工具返回的结果

... (重复 Thought/Action/Observation 直到任务完成)

Thought: 我现在知道最终答案了
Final Answer: 返回给用户的答案

现在开始!

用户问题: {用户的输入}
Thought: {让LLM开始思考}
```

这个提示词模板的关键在于定义了清晰的格式规范。LLM被训练成能够遵循这种格式，每次输出都会包含"Thought"、"Action"、"Action Input"这些字段。Agent执行器会解析LLM的输出，提取出要调用的工具名称和参数，然后执行工具，再把结果以"Observation"的形式反馈给LLM，开启下一轮循环。

## 3.3 工具描述

前面说了，在实现Agent的提示词中，要给到大模型工具选择，对于工具而言，工具的描述(Description)至关重要。它直接影响LLM能否正确选择和使用工具。在编写工具描述时总结出了几个原则:

第一是明确使用场景。比如TodoAdd工具的描述会说"当用户需要创建待办事项时使用"，这样LLM就知道什么时候该调用这个工具。

第二是详细说明参数格式。特别是对于复杂参数，要说清楚每个字段的含义、类型、以及如何获取。比如TodoAdd的描述里会强调:"executeIds是用户ID数组，如果用户提到人名，必须先用user_list工具查询ID"。这种显式的提示能大大减少LLM的错误调用。

第三是说明工具之间的依赖关系。比如"deadlineAt必须是Unix时间戳，如果用户输入的是自然语言时间，要先用time_parser转换"。这样LLM就知道要先调用time_parser再调用todo_add。

第四是提供输出示例。告诉LLM工具会返回什么样的结果，这有助于LLM在下一轮循环中正确解析和使用工具的输出。

## 3.4 待办创建的完整过程

基于前面的分析，下面来看一下AI创建待办的完成过程是怎样的，来看看Agent如何理解用户需求并完成任务

![BlockNote image](https://ls8sck0zrg.feishu.cn/space/api/box/stream/download/asynccode/?code=NTA1MWRkOTc0YjkwYmIxZjg1MTliOGQzYjVhMGE2MjZfUVN4QnJMWGFLZFh3VzlKQlplMlJOdFZPeGczM29YbnVfVG9rZW46R0p0SGJsUmZkb1F4VGR4ck1uS2N0eDlCbkpiXzE3Nzc4MzY2MjE6MTc3Nzg0MDIyMV9WNA)

从这个完整的时序图可以清楚地看到，Agent处理这个复杂任务经历了五轮思考-行动-观察的循环:

第一轮:查询第一个执行人 LLM分析用户输入后识别出关键信息:两个人名(张三、李四)、一个时间表达(明天下午3点)、一个待办标题(季度总结报告)。判断需要创建待办，但首先要解决人名到用户ID的转换问题。于是先调用user_list工具查询"张三"，获得用户ID。

第二轮:查询第二个执行人 有了张三的ID后，LLM继续推理，发现还需要李四的ID，于是再次调用user_list工具。这展示了Agent的自主性:它知道有两个人名需要处理，会自动调用两次工具，而不需要我们预先编写循环逻辑。

第三轮:解析时间表达 两个用户ID都准备好了，接下来LLM发现"明天下午3点"是自然语言表达，需要转换为系统能理解的Unix时间戳，于是调用time_parser工具。这个工具内部也会调用LLM来做时间解析，充分利用了LLM对自然语言的理解能力。

第四轮:创建待办事项 此时所有必要信息都已齐全:用户IDs、时间戳、待办标题。LLM做出一个很聪明的判断:用户说"各创建一个"不是让我创建两个独立的待办，而是创建一个由两人共同执行的待办。于是调用todo_add工具，传入两个用户ID到executeIds数组中。

第五轮:返回结果 待办创建成功后，LLM判断任务已完成，组织一个清晰的答复返回给用户，包含待办标题、执行人、截止时间和待办ID等关键信息。

整个过程完全由Agent自主完成，我们不需要编写任何流程控制代码。这就是Agent的强大之处:它不是按照预设的流程执行，而是根据实际情况动态规划和调整。即使用户的需求更复杂，比如涉及三个人、多个时间点，Agent也能自主分解任务并正确执行。

## 3.5 待办处理器实现

TodoHandle是一个典型的专业处理器，它配备了待办相关的工具集，能够处理待办的创建、查询、修改等各种操作。

```go
type TodoHandle struct {
    *baseChat
}

func NewTodoHandle(svc *svc.ServiceContext) *TodoHandle {
    return &TodoHandle{
        baseChat: NewBaseChat(svc， []tools.Tool{
            toolx.NewUserList(svc)，   // 用户列表查询工具
            toolx.NewTimeParser(svc)， // 时间解析工具
            toolx.NewTodoAdd(svc)，    // 待办创建工具
            toolx.NewTodoFind(svc)，   // 待办查询工具
        })，
    }
}

func (t *TodoHandle) Name() string {
    return "todo"
}

func (t *TodoHandle) Description() string {
    return "suitable for todo processing， such as todo creation， query， modification， deletion， etc"
}
```

这个处理器的Name是"todo"，Description告诉路由器它适合处理待办相关的各种操作。当路由器把请求分发给TodoHandle时，Agent会根据具体的用户输入决定调用哪些工具。比如用户说"创建待办"就会调用TodoAdd，用户说"查询我的待办"就会调用TodoFind。

工具之间的配合也很巧妙。UserList和TimeParser是辅助工具，它们不直接操作业务数据，而是帮助其他工具把用户输入转换为系统能理解的格式。比如用户说"明天"，TimeParser会把它转换为具体的Unix时间戳;用户说"王员工"，UserList会查询数据库找到对应的用户ID。这种设计让TodoAdd这样的核心工具可以专注于业务逻辑，而不用处理各种输入格式的解析。

## 3.6 默认处理器实现

DefaultHandler是一个特殊的处理器，它不调用任何工具，只是用LLM进行普通的对话。这个处理器的作用是兜底，当用户的问题不属于任何专业领域时，比如闲聊、通用问答，就会交给它来处理。

```go
func NewDefaultHandler(svc *svc.ServiceContext) *DefaultHandler {
    // 定义AI助手的基础提示词
    template := "you are an all-round assistant， please help me answer this question: \n\n<< input >>\n{{.input}}"

    prompt := prompts.PromptTemplate{
        Template:       BASE_PROMPT_TEMPLATE + template + "\n\n" + OUT_PROMPT_TEMPLATE，
        InputVariables: []string{langchain.Input}，
        TemplateFormat: prompts.TemplateFormatGoTemplate，
        PartialVariables: map[string]any{
            "chatType": fmt.Sprintf("%d"， domain.DefaultHandler)，
            "data":     "solution"，
        }，
    }

    return &DefaultHandler{
        svc: svc，
        c:   chains.NewLLMChain(svc.LLMs， prompt， chains.WithCallback(svc.Callbacks))，
    }
}
```

DefaultHandler的提示词很简洁，就是告诉LLM你是一个全能助手，帮用户回答问题。这种通用性让它能够处理各种意料之外的输入，保证了系统的鲁棒性。即使路由器出现误判，或者用户的需求确实不属于任何专业领域，用户也能得到一个有意义的回复。

# 4. 工具系统设计

工具（Tool）是连接AI和业务系统的桥梁，它让AI从"能说"变成了"能做"。在设计工具系统时，核心思路是:每个工具只做一件事，但要把这件事做到极致。

## 4.1 工具接口规范

LangChain定义了统一的Tool接口，每个工具都需要实现Name()、Description()和Call()三个方法。Name是工具的唯一标识，LLM通过这个名称来引用工具;Description非常重要，它告诉LLM这个工具能做什么、什么时候应该用、怎么用;Call是实际的执行逻辑。

工具的Description编写有很多技巧。如果描述写得不够清楚，LLM经常会误用工具或者传错参数。所以在每个工具的Description里都详细说明了使用场景、参数格式、注意事项。比如TodoAdd的Description里专门强调了:"如果用户提到人名，必须先用user_list工具查询用户ID，然后再用这个ID"，这样能大大减少LLM的错误调用。

## 4.2 待办创建工具

TodoAdd是一个典型的业务工具，它封装了创建待办事项的完整流程。这个工具使用了结构化输出解析器，定义了待办事项的所有字段:标题、截止时间、描述、执行人列表等。这里只是以待办工具为例进行分析，其他的比如审批工具也是类似的实现。

```go
func NewTodoAdd(svc *svc.ServiceContext) *TodoAdd {
    return &TodoAdd{
        svc:      svc，
        callback: svc.Callbacks，
        // 配置结构化输出解析器
        outputparser: outputparserx.NewStructured([]outputparserx.ResponseSchema{
            {
                Name:        "title"，
                Description: "todo title"，
            }， {
                Name:        "deadlineAt"，
                Description: "the deadline Unix timestamp (in seconds). You MUST use the time_parser tool first to convert the user's time expression to a timestamp"，
                Type:        "int64"，
            }， {
                Name:        "executeIds"，
                Description: "list of participating users in the backlog. the data type is a set of string ids"，
                Type:        "[]string"，
            }，
        })，
    }
}

func (t *TodoAdd) Call(ctx context.Context， input string) (string， error) {
    // 解析AI输入为结构化数据
    data， err := t.outputparser.Parse(input)
    if err != nil {
        return ""， err
    }

    // 调用API创建待办事项
    res， err := curl.PostRequest(token.GetTokenStr(ctx)，
        t.svc.Config.Host+"/v1/todo"， data)

    // 解析响应获取创建的待办ID
    var idResp domain.IdRespInfo
    json.Unmarshal(res， &idResp)

    return "Success\ncreated todo id : " + idResp.Data.Id， nil
}
```

这个工具的设计有几个亮点。第一是使用了结构化输出解析器，它会自动生成格式说明并注入到工具的Description里，告诉LLM应该按什么格式输出。比如deadlineAt字段的类型是int64，LLM就知道要输出数字而不是字符串。第二是强调了工具之间的依赖关系，明确告诉LLM必须先用time_parser转换时间，这样能避免LLM直接传一个"明天"这样的字符串。第三是返回了创建成功的待办ID，这个信息会被记录到对话历史中，用户稍后可以引用这个ID进行修改或查询。

## 4.3 基础工具设计

UserList和TimeParser是两个非常实用的基础工具，它们不直接操作业务数据，而是提供格式转换服务。这种设计让其他工具可以专注于业务逻辑，而不用处理各种输入格式的解析。

TimeParser工具特别有意思，它能把各种自然语言的时间表达转换为Unix时间戳。比如"明天下午3点"、"下周五"、"3天后"这些表达，TimeParser都能准确转换。而且它还支持相对时间和绝对时间的混合，比如"明天下午3点到5点"。实现这个工具时，我没有自己写解析逻辑，而是让LLM来做这个转换。LLM对自然语言的理解能力远超任何手写的规则，而且能处理各种边界情况。

UserList工具解决了另一个常见问题:用户在对话中通常会用人名，但系统需要的是用户ID。这个工具会根据姓名模糊查询用户列表，然后返回匹配的用户ID。如果找到多个匹配项，它会全部返回，让LLM根据上下文来选择正确的那个。

# 5. 多会话记忆设计

记忆管理是AI助手体验的关键。如果AI不能记住之前说过的话，每次对话都像第一次见面，这种体验是很糟糕的。但是记忆管理也有很多技术挑战:如何隔离不同用户的记忆?如何控制记忆的长度?如何在记忆和性能之间取得平衡?

## 5.1 会话隔离机制

多会话隔离是记忆管理的第一个挑战。在一个多用户的系统中，每个用户都应该有自己独立的对话历史，用户A和AI聊的内容不应该影响到用户B。设计的Memoryx组件用一个简单而有效的方式实现了这个隔离。

![BlockNote image](https://ls8sck0zrg.feishu.cn/space/api/box/stream/download/asynccode/?code=ODc4NDYxMDVkM2Q5YmM2ZDFkNjIyMTQ2ZTYzMjFiY2Ffb2pJWE5GUk1yUzN2Tjk1dkdEQUx3ZmVPRnRybndwY2FfVG9rZW46WGI1SmI3NnpabzBwZXN4blk2Z2N2Wm03blRnXzE3Nzc4MzY2MjE6MTc3Nzg0MDIyMV9WNA)

从这个架构图可以看出，Memoryx管理器维护了一个map，键是用户ID，值是该用户的Memory实例。当用户发起请求时，系统会从JWT Token中提取用户ID，然后注入到Context中。Memoryx根据Context中的用户ID查找对应的Memory实例，如果是该用户第一次对话，就创建一个新的Memory实例并存入map;如果已经存在，就直接复用。

这种设计的好处是简单而有效。每个用户的对话历史完全隔离，用户A说"我叫张三"，不会影响到用户B的对话。而且使用互斥锁保护map的并发访问，保证了在高并发场景下的数据安全。

## 5.2 摘要缓冲策略

记忆的第二个挑战是如何控制长度。对话历史不能无限增长，否则会有两个问题:一是Token消耗越来越大，每次对话都要把全部历史发给LLM，成本很高;二是LLM的上下文窗口有限，太长的历史会超出限制。

这里采用的是摘要缓冲(Summary Buffer)策略，这是一个很巧妙的设计:保留最近的N条消息作为"短期记忆"，更早的消息则通过LLM总结成"长期记忆"。

![BlockNote image](https://ls8sck0zrg.feishu.cn/space/api/box/stream/download/asynccode/?code=NmVkZmU1ZTYzZjIwYjBjZTFjNWU0Yjk1NTM5MTNmODhfWlJ0Mmg1aG40VkU3WTFWNjExeURYeXZiYWVFNXNoUmRfVG9rZW46UFVwZWJSOXNib1dvVzJ4MHpibmMyVEg0blNnXzE3Nzc4MzY2MjE6MTc3Nzg0MDIyMV9WNA)

从这个流程图可以看出，摘要缓冲的核心机制是动态平衡。当对话消息少于阈值(比如50条)时，所有消息都作为短期记忆原样保存。一旦超过阈值，就会触发总结流程:提取最早的一批消息，调用LLM生成一段摘要，然后用这段摘要替换原始消息。

这样设计的好处是既保证了记忆的连贯性，又控制了Token消耗。AI可以从摘要中了解更早的对话背景，同时对最近的对话保持完整的细节记忆。在实际使用中，这个策略效果很好:即使对话持续了几百轮，Token消耗也能保持在一个可控的范围内，而AI对上下文的理解不会明显下降。

阈值的设置是个经验值。这里设置的是50条消息，这是在成本和效果之间的一个平衡点。如果对话特别长或者对成本特别敏感，可以设置成30或40;如果更看重记忆效果，可以设置成80或100。这个参数可以根据实际场景灵活调整。

## 5.3 记忆在对话流程中的作用

记忆管理不是孤立的，它贯穿于整个对话流程的始终。这里用一个完整的例子来展示记忆是如何工作的。

1. 场景一：用户第一次对话
   - 用户说:"我叫张三，请帮我创建一个待办"
   - 系统为用户创建新的Memory实例
   - 保存对话:User: "我叫张三，请帮我创建一个待办" / AI: "好的，请问待办内容是什么?"
   - 此时Memory中只有这一轮对话
2. 场景二：用户继续对话
   - 用户说:"明天下午3点前完成季度报告"
   - 系统从Memory加载历史:发现用户叫张三，正在创建待办
   - AI理解上下文，知道"季度报告"是待办的标题，"明天下午3点"是截止时间
   - 完成待办创建，保存新的对话到Memory
3. 场景三：用户切换话题
   - 用户说:"我的待办都有哪些?"
   - 系统加载Memory，AI看到完整的对话历史
   - AI理解"我的待办"指的是张三的待办(从历史中知道用户是张三)
   - 查询待办并返回，保存对话到Memory
4. 场景四：长期对话后的摘要
   - 经过50轮对话后，Memory触发总结
   - 早期的对话被总结为:"用户张三创建了多个待办事项，查询过审批流程，上传过PDF文档..."
   - 最近的50轮对话保持原样
   - 后续对话中，AI既能从摘要了解背景，又能从最近对话获得细节

## 5.4 记忆输出过滤

还有一个重要的细节:记忆中保存的应该是"纯净"的对话内容，而不是系统的技术格式。AI助手的输出通常是结构化的JSON，包含chatType、data等字段，这些是给系统用的元信息，不应该污染对话历史。

所以实现了一个输出过滤器，在保存记忆时自动提取data字段的实际内容，过滤掉技术格式。比如AI返回`{"chatType": 1， "data": "已成功创建待办"}`，保存到记忆时只会记录"已成功创建待办"这个真实的回复内容。

这个过滤让记忆更加干净，AI在加载历史时能够专注于对话本身，而不会被JSON格式、字段名称等技术细节干扰，从而提供更自然的对话体验。

## 6.1 AI对话处理流程

从这个完整的时序图可以看出，一次AI对话经历了多个环节:路由决策、处理器选择、Agent执行、工具调用、记忆保存。每个环节都有明确的职责，整个流程是一个完整的闭环。

路由决策阶段，LLM会接收到用户的当前输入、历史对话上下文、以及所有可用处理器的描述。基于这些信息，LLM做出判断，选择最合适的处理器。比如用户说"帮我创建一个明天下午3点前完成的待办"，LLM会分析出这是待办相关的操作，返回destination: "todo"。

进入专业处理器后，Agent执行器开始工作。Agent不是一次性完成任务，而是一个循环过程:调用LLM分析任务，LLM决定调用哪个工具，调用工具获得结果，再调用LLM分析下一步该做什么。这个循环会持续到任务完成或者达到最大步数限制。

在上面的例子中，Agent会分三步完成任务:先用time_parser把"明天下午3点"转换为Unix时间戳，再用user_list查询"王员工"的用户ID，最后用todo_add创建待办。这三个步骤完全由LLM自主决定，我们不需要编写任何调度逻辑。

# 7. 性能优化

1. 第一个优化点是记忆加载的性能。早期实现中，每次对话都会完整加载用户的历史记录，当对话次数很多时，加载会很慢。引入摘要缓冲后，这个问题得到了明显改善。现在只有最近50条消息会完整加载，更早的对话已经被总结成摘要，加载速度大大提升。
2. 第二个优化是工具调用的并发控制。有些场景下，Agent会连续调用多个工具，比如批量查询待办事项。如果串行调用，总耗时会比较长。虽然LangChain目前还不支持工具的并行调用，但我们在工具内部实现了批量操作的优化，比如TodoFind工具可以一次查询多个待办，而不是逐个查询。
3. 第三个优化是LLM调用的缓存。我们发现有些问题用户会反复问，比如"今天有哪些待办"、"本月的审批统计"这种。对于这类查询型的问题，结果在短时间内不会变化，完全可以缓存起来。我们在Router层加入了简单的缓存机制，相同的输入在一定时间内会直接返回缓存的结果，避免了重复的LLM调用。
4. 第四个优化是提示词的精简。提示词的长度直接影响LLM的响应时间和Token消耗。我们不断优化各个处理器和工具的Description，在保证功能的前提下尽量精简表达，去掉冗余的说明。这个优化看起来很小，但累积起来效果很明显，整体的Token消耗降低了约20%。

# 8. 方案优势与不足

## 8.1 优势

1. 架构的灵活。多层架构让各个组件高度解耦，新增功能非常简单。比如要增加"会议管理"功能，只需要实现一个MeetingHandle和对应的工具集，在NewChat方法里注册一下就行了，不需要改动路由器、记忆管理等核心组件。这种插件化的设计让系统能够快速响应业务需求的变化。
2. 智能化程度高。我们没有用关键词匹配这种传统的意图识别方式，而是让LLM真正理解用户的自然语言输入。这带来了两个好处:一是准确性更高，LLM能够处理各种复杂的表达方式;二是免维护，不需要不断添加规则或者重新训练模型，只要把处理器的Description写清楚，LLM就能做出正确的判断。
3. 会话体验的提升。多会话记忆管理让每个用户都有独立的对话上下文，AI能够记住之前的对话内容，理解代词的指代，这让对话更加自然流畅。而且摘要缓冲策略在保证记忆效果的同时控制了成本，即使是很长的对话，系统也能保持高效运行。
4. 系统可靠性强。多层降级策略保证了即使某个环节出现问题，用户也能得到合理的响应。路由失败有默认处理器兜底，工具调用失败有错误处理机制，记忆加载失败有默认记忆实例。这些保护措施让系统在各种边界情况下都能正常工作。

## 8.2 不足

1. 当前的处理器和工具都是在代码里硬编码注册的，每次新增功能都要修改代码。更好的方式是实现一个插件系统，工具可以通过配置文件或者注解自动注册，甚至支持热插拔。这样可以大大提升系统的灵活性，也降低了开发和部署的复杂度。
2. 多Agent协作，当前的架构是单Agent的，一个请求只能由一个处理器处理。但实际业务中，有些任务需要跨域协作，比如"帮我安排明天的会议，并给相关人员创建待办提醒"这种请求就涉及到会议管理和待办管理两个领域。未来可以考虑实现多Agent协作机制，让不同的处理器可以相互调用，共同完成复杂的任务。
